# Аудит Orbit Console

Проверены Prisma-модели, CRUD API, компоненты панели, автономный worker и локальные тесты. Выводы относятся к этому проекту; живые поисковые выдачи и платные внешние сервисы в ходе аудита не запускались.

## Исправлено в этом обновлении

| Функция | Что мешало работе | Исправление |
| --- | --- | --- |
| Поисковые и витальные фразы | Поля находились за флажком в режиме прямого URL | Явный сценарий поиска выбран по умолчанию, textarea и количества фраз в таблице |
| Изменение задач | API поддерживал PATCH, кнопки редактирования не было | Полный редактор сценария, фраз, домена, профиля и статуса |
| Повторный запуск | Завершённая задача не имела кнопки запуска | Постановка в очередь без обнуления счётчика и с тем же профилем |
| Профили | API был доступен, отдельной страницы не было | Имена, создание, переименование, пауза, сводка сессии и кнопка прогрева |
| Ротация IP | URL вводился только в широкую таблицу существующих прокси | Поле при ручном добавлении и массовом импорте, редактирование и показ/скрытие ссылки |
| Учётные данные прокси | PATCH был доступен только через API | Редактор адреса/порта/логина/пароля; прежний пароль не раскрывается |
| OpenAI | Поле сохраняло ключ лишь в памяти браузера | Постоянный Settings.openaiApiKey; worker читает базу, затем окружение; ответ API без секретов |
| Обновление статусов | Данные загружались один раз | Опрос раз в пять секунд и ручное обновление |
| Состояние исполнителя | Задачи назывались выполняющимися даже без процесса | Отдельный статус процесса; задачи обозначены как находящиеся в очереди |
| Версионирование | Правило profiles/ исключало также исходники страницы/API профилей | Исключена только корневая папка с секретными файлами сессий /profiles/ |

Автоматическое создание мобильного отпечатка, восстановление cookies/localStorage и логика прогрева/поиска уже реализованы в worker. В панели показаны их доступные сценарии и параметры; генерация отпечатка не требует ручной настройки.

## Что ещё необходимо сервису

### Приоритет 1 — результаты и наблюдаемость

1. **Журнал Execution.** Добавлены currentExecutions/targetExecutions и история успешных использований ProfileProjectHistory. Таблица TaskExecution из незавершённой системы назначений пока не подключена к исполнителю как полный журнал запусков. Нужны отдельные записи запусков с taskId/profileId/proxyId, началом/окончанием, результатом, кодом ошибки и выбранным сценарием. Без этого нельзя достоверно показывать «выполнено сегодня», длительности, успешность, текущий шаг и историю ошибок. Секреты и полный URL с чувствительными параметрами в журнал не помещать.
2. **Heartbeat и управление процессом.** Текущий индикатор проверяет живой PID из файла блокировки на том же сервере. Это не доказывает, что процесс продвигается по задаче. Нужны heartbeat, текущая задача/шаг, управляющий supervisor и понятные операции запуска/остановки. Веб-кнопка запуска сейчас отсутствует: процесс запускается отдельно.
3. **Проверка прокси и закрепление за профилем.** isActive — ручной переключатель, временные ошибки/cooldown хранятся только в памяти worker. Нужны последнее успешное соединение, измеренный внешний IP, дата ротации, причина ошибки и стабильное назначение прокси профилю. HTTP 2xx от rotationUrl не подтверждает фактическую смену IP.
4. **Ошибки и попытки.** Worker пишет ошибки в stdout, но не сохраняет статус каждой неудачной попытки в базе. Сейчас статус failed можно выставить через API вручную; он не является полноценной историей отказов. Нужны лимит повторов, retryAfter и разделение временных/постоянных ошибок.

### Приоритет 2 — эксплуатация

5. **Авторизация перед общим доступом.** Панель работает как локальный инструмент. API проверяет origin для браузерных записей, но не аутентифицирует оператора. Для размещения вне localhost нужны вход, роли и аудит изменений; origin-проверка не заменяет контроль доступа.
6. **Защита и резервное копирование данных.** Ключи/пароли находятся в SQLite, сессии — в приватных JSON. Нужны документированная политика хранения, шифрование секретов, согласованные резервные копии SQLite и profiles, тест восстановления и очистка старых сессий.
7. **Очередь и расписания.** Выполнение последовательное, один worker на файл базы. Для нескольких исполнителей нужны атомарный захват задачи, блокировка профиля, периодический запуск, дедупликация и восстановление после сбоя. При BullMQ необходимо продление блокировок; lockDuration минимум 600000 мс для длинных поисковых посещений.
8. **Настройки процесса из панели.** Таймауты, схема прокси, режим окна, длительность прямого посещения, выбор RuCaptcha/2Captcha и пул доноров задаются окружением/константой. Сейчас они показаны как сведения. Редактирование потребует валидируемой постоянной конфигурации и согласованного применения в автономном процессе.

### Приоритет 3 — контроль качества и масштаб

9. **Адаптеры поисковиков.** Локальные тесты покрывают шаблоны main/iframe, AJAX и popup. Нет проверенного набора живых версий выдачи и механизма фиксации неизвестной разметки. Для поддержки нужны разрешённые тестовые сценарии, диагностика и обновление селекторов.
10. **История сессий профиля.** Сейчас хранится один последний успешный storageState; нет версий, экспорта/импорта, архива, связи прокси и удаления профиля с понятной политикой связанных задач. Наличие cookies не подтверждает конкретную историю посещений или оценку профиля сторонним сервисом.
11. **Большие таблицы.** API возвращает все записи, фильтрация выполняется в браузере. Для роста нужны серверная пагинация, поиск, сортировка и ограничение частоты запросов.
12. **Согласованность файла и базы.** Публикация JSON выполняется рядом с транзакцией счётчика, но filesystem и SQLite не имеют общей транзакции. При аварии после переименования файла до commit возможна рассинхронизация. Нужен журнал публикации/восстановление или хранение версии состояния в транзакционном хранилище.

Предлагаемый следующий этап: Execution + heartbeat + сведения о прокси. Он даст настоящую дневную статистику, прогресс и причины неудач, которые сейчас недоступны интерфейсу.
