# Orbit — Browser Automation Console

Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui и Prisma ORM 6.19 с файловой SQLite.

## Локальный запуск

Требуются Node.js 22+ и pnpm 11.

```bash
pnpm install
cp .env.example .env
pnpm db:setup
pnpm auth:user
pnpm dev
```

Откройте http://127.0.0.1:3000. Если `.env` уже настроен, сохраните его вместо копирования шаблона.

В шаблоне `DATABASE_URL="file:../.orbit-runtime/orbit.db"` создаёт новую базу в `.orbit-runtime/`. Относительные пути Prisma считает от папки схемы. Добавлен `.gitignore` для новых локальных данных, но исходный репозиторий уже содержит старые SQLite, профили, `node_modules` и `out`; они не используются в пакете серверного релиза. Миграции и `.env.example` сохраняются в проекте.

## Авторизация

Все страницы панели и API требуют активную серверную сессию. Вход: `/login/`,
почта по умолчанию `seo@uniofweb.ru`, пароль создаётся командой `pnpm auth:user`
и записывается в приватный файл `.auth-credentials` (0600). Публичной регистрации
нет. Пароль хранится в SQLite как scrypt-хеш; сессия действует 12 часов,
выход отзывает её на сервере. После 20 попыток входа за 15 минут включается
ограничение; успешный вход сбрасывает счётчик.

Задайте `APP_ORIGIN` точно по адресу приложения, без завершающего `/`.
На сервере: `https://orbit.server-uniofweb.ru`; Secure-cookie включается для HTTPS.
`AUTH_EMAIL` определяет единственный разрешённый адрес. Сменить пароль и отозвать
сессии: `ORBIT_CREDENTIALS_FILE=/private/new-credentials pnpm auth:user --reset`.
CLI-клиентам нужно войти через POST `/api/auth/login/` с JSON `{email,password}`
и передавать полученную cookie в последующих запросах.

Опционально можно добавить стартовые примеры:

```bash
pnpm db:seed
```

Seed повторяемый: существующие записи не перезаписываются. Прокси примеров используют документальные адреса и изначально отключены. Счётчики примеров равны нулю.

## Серверный запуск

Подготовлены systemd unit, конфигурации веб-сервера и пакетирование релиза:
[инструкция развёртывания](deploy/README.md). Все операции с кодом и данными
выполняются от www-data; root используется для администрирования служб.

```bash
pnpm db:setup
pnpm build
pnpm start
```

Статический экспорт удалён: API требует Node.js и постоянного записываемого диска. Сохраняйте SQLite-файл между перезапусками и релизами. Перед запуском нового релиза применяйте `pnpm db:deploy`. Для разработки изменений схемы используйте `pnpm db:migrate --name имя_миграции`.

Опубликованный ранее адрес `chatgpt.site` содержит старое статическое демо. Эта серверная версия не развёрнута там: файловая SQLite не является постоянным хранилищем Cloudflare Workers. Для публикации данной версии нужен Node.js-хост с диском; альтернативой для Workers будет отдельная адаптация к D1 или libSQL.

## Модели

`prisma/schema.prisma` содержит модели:

- `Project`: `id`, `name`, `targetUrl`, строковый `yandexRegionId`, `createdAt`, `updatedAt`, связи с задачами и историей.
- `Task`: `projectId`, `profileId`, `taskType`, `url`, `searchEngine`, `searchQueries`, `vitalPhrases`, `targetKeywords`, `status`, `targetExecutions`, `currentExecutions`, `createdAt`.
- `Profile`: UUID, имя, `status` (`queued`, `warming_up`, `ready`, `failed`, `banned`), `warmupScore`, `isEnabled`, `warmedAt`.
- `ProfileProjectHistory`: `profileId`, `projectId`, `executedAt`; `source` отличает импорт старых данных от новых выполнений.
- `Proxy`: адрес, порт, авторизация, `isActive`, `rotationUrl`.
- `Settings`: ключи интеграций и настройки сервиса. Ключи не возвращаются через API.

Статусы задач: `running`, `paused`, `completed`, `failed`. Целевая задача создаётся внутри проекта; прогрев хранится отдельно в `WarmupJob` и не входит в список задач. Целевой домен определяется из `Project.targetUrl`, отдельного `Task.targetDomain` больше нет.

`currentExecutions` и `warmupScore` обновляются исполнителем, редактировать их через API нельзя. План `targetExecutions` можно увеличить без обнуления прогресса; нельзя уменьшить его ниже уже выполненного количества. Выключение профиля сохраняется отдельно от его статуса и не означает блокировку.

## CRUD API

| Роут | Методы |
| --- | --- |
| `/api/projects/` | GET — список; POST — создание |
| `/api/projects/:id/` | GET/PATCH/DELETE; GET включает последние 100 записей истории |
| `/api/projects/:id/run/` | GET — состояние исполнителя; POST `{ "action": "start" }` или `{ "action": "stop" }` |
| `/api/tasks/` | GET — список (опционально `?projectId=...`); POST — создание |
| `/api/tasks/:id/` | GET — запись; PATCH — частичное обновление; PUT — полная замена изменяемых полей; DELETE — удаление |
| `/api/tasks/:id/live/` | GET — состояние запуска, события и версия снимка вкладки |
| `/api/tasks/:id/live/screenshot/` | GET — последний JPEG-кадр текущего запуска |
| `/api/proxies/` | GET — список; POST — создание или массовый импорт |
| `/api/proxies/:id/` | GET — запись; PATCH — частичное обновление; PUT — полная замена изменяемых полей; DELETE — удаление |
| `/api/profiles/` | GET — список; POST — создание по `{ "name": "Название" }` |
| `/api/profiles/:id/` | PATCH — изменение имени, статуса или isEnabled |

### Создание задачи внутри проекта

Сначала создайте проект через `/projects/` или POST `/api/projects/`:

```json
{
  "name": "QA каталога",
  "targetUrl": "https://example.com/catalog",
  "yandexRegionId": "213"
}
```

На странице проекта кнопка «Настроить расписание» открывает сетку 7 × 24: зелёные часы разрешают новые выполнения всех задач проекта. Выбор работает кликом и прямоугольником при перетягивании; начните с зелёной ячейки для снятия выделения. Быстрые варианты: будни 08:00–20:00, ежедневно 08:00–20:00, все будни, все выходные, 70% случайных ячеек, все часы, очистка. Верхняя граница 20:00 не включается. Часовой пояс задаётся отдельно (по умолчанию `Europe/Moscow`), учитывает переходы на летнее время.

Расписание хранится в `Project.scheduleHours` (строка из 168 нулей/единиц, понедельник первым) и `scheduleTimezone` (часовой пояс IANA); POST/PATCH проекта принимает оба поля. По умолчанию разрешены все часы, пустая сетка запрещает новые старты. Исполнитель проверяет актуальное расписание в транзакции перед резервированием профиля/прокси, остаётся в ожидании вне расписания и продолжает автоматически, когда время разрешено. Уже начатые сеансы завершаются; приостановленные задачи и прогрев не меняются. Запущенный исполнитель необходим для автоматического продолжения. Проверка: `node --test tests/project-schedule.test.mjs`; браузерный тест `tests/project-schedule-ui.test.mjs` требует локальный `API_TEST_BASE_URL` и отдельную тестовую БД.

Затем откройте `/projects/{id}/` и нажмите «Создать задачу». API принимает:

```json
{
  "projectId": "id-проекта",
  "url": "https://example.com/catalog",
  "targetExecutions": 3,
  "targetKeywords": ["каталог", "QA"],
  "status": "paused"
}
```

Если прямой URL не указан, берётся `Project.targetUrl`. Поисковые поля существующего сценария — `searchEngine`, `searchQueries`, `vitalPhrases`; фразы принимаются массивами и вводятся по строкам в textarea. Домен в форме доступен только для чтения и берётся из проекта. Ответ задачи включает `project` и nullable `profile`: профиль выбирается исполнителем перед каждым выполнением.

При вводе поискового запроса исполнитель повторно выбирает редактор после нажатия
на мобильную строку поиска: раскрытая форма может заменить прежнее поле. Если
подготовить ввод не удалось, выполняется один возврат на главную страницу того же
поисковика в той же браузерной сессии с повторным вводом полного запроса, включая
витальную часть. Ожидание поля или его активации ограничено пятью секундами
(либо меньшим тайм-аутом навигации). Блокирующее окно и остановка задачи прерывают
восстановление; уже отправленный поиск таким способом не повторяется.
Журнал различает поиск поля, его открытие, ввод и отправку запроса; повторная
ошибка получает конкретный код вместо общего `execution_failed`.

В задаче есть необязательный `dailyExecutionLimit`: `null` (в форме «-» или пусто)
оставляет выполнение без дневного ограничения, в разрешённые часы проекта.
Число от 1 до 10 000 задаёт дневной максимум успешных выполнений. Текущие сеансы
резервируют места; ошибки освобождают их. День определяется по началу сеанса
в `Project.scheduleTimezone`, поэтому переход через полночь не переносит его
квоту в следующий день. Общий план `targetExecutions` и число потоков продолжают
действовать независимо.

Планировщик сохраняет случайные моменты запуска в `TaskDailyPlan`: интервалы
не фиксированы, а исполнения распределяются по оставшимся разрешённым окнам
текущего дня. При старте посреди дня учитываются уже выполненные и текущие
сеансы. Перезапуск сохраняет план; если время очередного запуска пропущено
более чем на пять минут, оставшаяся часть распределяется заново без залпа
накопленных запусков. Изменение лимита, общего плана, часов или часового пояса
также пересчитывает только оставшуюся часть. Резервирование профиля и проверка
квоты выполняются в одной транзакции SQLite. После окончания суток создаётся
новый план; без доступных ресурсов фактических выполнений может быть меньше
лимита. API возвращает `dailyExecutionsToday`, `dailyReservedToday`,
`nextExecutionAt` и `dailyWaitReason`, не раскрывая весь календарь запусков.

PUT/PATCH проверяют итоговые параметры после объединения с записью. Проект существующей задачи фиксирован; для другого проекта создайте отдельную задачу. `id`, `createdAt`, `currentExecutions` не изменяются клиентом.

В разделе «Профили» можно создать от 1 до 1000 профилей за раз (кнопки 100/300/500/1000). Каждый автоматически получает запись `WarmupJob`. Отдельный процесс `pnpm worker:warmup` обслуживает очередь даже без запущенного проекта. Статус `ready` выставляется только после успешного обхода и сохранения сессии браузера. На странице доступны очередь, прогресс, ошибки, три автоматические попытки с задержкой, массовая пауза/возобновление/повтор, отключение и история использования.

Автопополнение поддерживает настраиваемый запас готовых профилей и учитывает дефицит текущих проектов. Неудачные и приостановленные прогревы входят в лимит незавершённых профилей, предотвращая бесконечное создание при неисправном прокси. Типовые настройки: запас 100, партия до 100, один параллельный прогрев, максимум 500 незавершённых. Если готовых профилей нет, основная задача ждёт.

Перед каждым целевым выполнением выбирается включённый прогретый профиль, который ещё не использовался в проекте. `ProjectProfileUse` резервируется атомарно, а `usedAt` устанавливается перед первым переходом на целевой сайт. После начала перехода профиль больше не участвует в этом проекте даже при ошибке или удалении задачи. Для другого проекта профиль доступен. `ProfileProjectHistory` хранит успешные выполнения.

`WorkflowLease` блокирует одновременно профиль и канал прокси между двумя исполнителями. По умолчанию одинаковый хост означает один канал; независимые каналы задаются в редакторе прокси. Одинаковая ссылка смены IP также блокируется совместно. Назначение прокси: общий, только прогрев или только задачи. С одним каналом работа чередуется; для параллельного прогрева и целевых задач нужны минимум два независимых канала. Активный прокси нельзя редактировать до окончания сессии. Истёкшие блокировки восстанавливаются после сбоя.

`GET /api/profiles/?page=1&search=&status=&queue=1` возвращает страницы по 25 записей; `/api/profiles/pool/` — сводку. `POST /api/profiles/actions/` принимает `profileIds` и `action`: `pause`, `resume`, `retry`, `enable`, `disable`. Ручное назначение профиля задаче и ручной перевод в `ready` запрещены.

Подробности миграции и сохранения старых данных: [PROJECTS_UPDATE.md](./PROJECTS_UPDATE.md).

### Создание прокси

```json
{
  "host": "192.0.2.10",
  "port": 8000,
  "username": "user",
  "password": "password",
  "isActive": true
}
```

Для POST `isActive` необязателен. Для PUT нужны все пять изменяемых полей, включая пароль.

Массовый импорт: `POST /api/proxies/` с `{ "proxies": [ ... ] }`, до 500 записей. Вся партия сохраняется в одной транзакции; ошибка или дубликат откатывает её целиком. Одиночный POST возвращает объект, массовый — массив. Пароли хранятся в SQLite, но не возвращаются ни одним API-методом и не попадают в клиентский список прокси.

Ответы: `200` — чтение/обновление; `201` — создание; `204` — удаление; `400` — ошибка полей/JSON; `403` — запись из другого источника; `404` — запись отсутствует; `409` — дубликат прокси; `415` — неверный Content-Type. Ошибки содержат `{ "error": "..." }`; ошибки валидации также содержат `details`.

## Интерфейс

- Данные загружаются из API при открытии приложения.
- Создание задач, пауза/продолжение, удаление задач и импорт/включение/отключение/удаление прокси сохраняются в SQLite.
- Поисковые и витальные фразы вводятся списками по строкам; метки задачи отделены от запросов. Счётчики и дата создания отображаются в таблице.
- Формы ждут подтверждения сервера; ошибки показаны пользователю, повторное сохранение блокируется на время запроса.
- Dashboard считает активные задачи, общие выполнения и включённые прокси по данным API. Дневная статистика убрана: для неё нужен журнал выполнений, которого нет в запрошенных моделях.
- Автономный исполнитель находится в `worker/`. Он проверяет соединение через прокси и увеличивает счётчик после успешного посещения. На странице проекта кнопка «Запустить проект» запускает отдельный процесс для задач этого проекта; «Остановить» прерывает текущую сессию без сохранения её результата.
- Ключи OpenAI и RuCaptcha сохраняются в `Settings` через `/api/settings/`; API возвращает только статусы. Прямые задачи по умолчанию используют локальный план и не обращаются к OpenAI. Старый режим OpenAI доступен только при явном `WORKER_PLAN_MODE=openai`.
- Для каждого прокси можно сохранить `rotationUrl`. Worker делает GET и ждёт 15 секунд перед запуском Chromium, затем обрабатывает reCAPTCHA v2/SmartCaptcha при обнаружении.

API_TEST_BASE_URL=http://127.0.0.1:3000 pnpm test:api

Интеграционные тесты работают только с локальным адресом. Используйте отдельную тестовую базу: тест авторизации временно меняет пароль разрешённой учётной записи и очищает счётчик входа. Проверяются CRUD, сохранение через независимый Prisma Client, валидация, исключение паролей из ответов, атомарность массового импорта и защита страниц/API. `DATABASE_URL` тестового процесса должен указывать на ту же тестовую базу, что и у сервера.

## Автономный worker

Для запуска из панели откройте `/projects/{id}/`, создайте задачу со статусом «В очереди» и нажмите «Запустить проект». Нужен хотя бы один включённый прокси; ключ OpenAI не нужен. Запуск из панели ограничен доменом проекта и поиском Яндекса; посещения сайтов конкурентов в этом режиме пропускаются. Процесс живёт отдельно от вкладки и сервера Next.js. Каждый проект запускает отдельный исполнитель: несколько проектов и задания внутри них работают параллельно. Число сеансов задания ограничено его настройкой потоков; профили и каналы прокси резервируются совместно через базу. Остановка проекта не останавливает остальные. Состояние процесса и логи хранятся локально в `.orbit-runtime/` (папка исключена из Git).

В таблице задач кнопка «Наблюдать» открывает `/tasks/{id}/live/`: текущий снимок браузера, переходы по страницам, HTTP-ответы и этапы сценария. Снимок обновляется примерно раз в 2,5 секунды, события — при обновлении страницы наблюдения; при остановке показан последний кадр текущего запуска. Пока браузер не открыл страницу (например, при проблеме с прокси), кадра нет, а ошибка видна в журнале. Данные наблюдения лежат в `.orbit-runtime/live/`, URL сохраняются без query и fragment; не публикуйте эту локальную папку как статические файлы.

Ручной режим CLI остаётся доступен:

```bash
pnpm worker:install
pnpm worker
# Одна попытка:
pnpm worker:once
```

Для целевых задач с прямым URL worker локально создаёт план из 10–15 действий и выполняет его с логами. Поиск и прогрев также работают без OpenAI. При явном `WORKER_PLAN_MODE=openai` остаётся прежняя интеграция с `gpt-4o-mini`; только в этом режиме нужен API-ключ. Инструкция и параметры — в [worker/README.md](worker/README.md). Worker использует ту же SQLite-базу; Next.js-сервер для его работы не требуется.

Worker использует только мобильные Android/iOS отпечатки. После успешного выполнения отпечаток, cookies и localStorage сохраняются в `profiles/{profileId}.json` и автоматически восстанавливаются через Playwright storageState. Каждая задача получает UUID профиля; при создании можно указать существующий UUID для общей сессии. Папка исключена из Git.


## Доступные элементы панели

- Создание и редактирование задач: явные сценарии «Поиск сайта», «Прямой URL», «Прогрев профиля», списки поисковых/витальных фраз, домен, поисковик, метки, именованный профиль, статус. Завершённые и ошибочные задачи можно запустить повторно; таблица фильтруется по фразам, статусу, сценарию и профилю.
- `/profiles`: создание, переименование и пауза профилей; запуск прогрева для выбранного профиля, UUID и безопасная сводка сохранённой сессии. Cookies/localStorage и полный отпечаток не возвращаются в UI.
- `/proxies`: массовый импорт, общий rotationUrl для текущего импорта, ручное добавление по hostname/IPv4, редактирование адреса, порта, логина, нового пароля и rotationUrl. Пустой пароль при редактировании сохраняет прежний. Тестовые ротации интерфейс не отправляет.
- `/settings`: режим локального плана, необязательные ключи интеграций, текущие параметры процесса, список доноров и инструкция запуска воркера.
- `/api/system/`: только безопасные сведения о состоянии процесса по блокировке SQLite и текущей конфигурации. Это не heartbeat и не журнал выполнения. Чувствительные пути, PID и ключи не возвращаются.
- Общие данные обновляются каждые пять секунд на видимой вкладке; ручная кнопка обновления находится в верхней панели. Статус «В очереди» означает доступность задачи для воркера, а не подтверждённое выполнение в эту секунду.

Подробный анализ недостающих частей сервиса: [SERVICE_AUDIT.md](SERVICE_AUDIT.md).

## Источники цифрового отпечатка

Настройки находятся в разделе «Профили»: `Авто` (MobileProxy с локальным резервом),
`Локальный генератор`, `Только MobileProxy`. API-токен MobileProxy хранится в Settings
и не возвращается через API; альтернативно используется `MOBILEPROXY_API_KEY`.
Официальные запросы идут только на `https://mpsapi.com/api.html` с Bearer-заголовком:
`get_my_proxy` для сопоставления прокси аккаунта и `fingerprint_generate` с
`proxy_id`, `os=android`, постоянным `seed`. Пароли прокси и кабинета в запросы
генерации не передаются. Прокси вне аккаунта в режиме «Авто» используют локальный
генератор; строгий режим сообщает ошибку. Таймаут API — 20 секунд, после ошибок
действует общая пауза 60 секунд. Список прокси кэшируется на 5 минут.

Локальный генератор работает без сети и строит согласованные Android/Chrome
конфигурации на основе встроенных семейств устройств. Профиль получает паспорт
при создании. В режиме «Авто» источник окончательно выбирается при первом
прогреве, когда известен прокси. После этого источник, seed и параметры сохраняются
даже при неудачном прогреве. Версия Chrome для нового паспорта согласуется с
реальным установленным движком до первого посещения. Старые сохранённые профили
принимаются без регенерации их параметров; новый источник не меняет прежние сессии.

Перед посещением сайтов локальная диагностическая страница, перехваченная внутри
браузера без внешнего запроса, сверяет UA, язык, CPU, экран, DPR, touch, память,
WebGL vendor/renderer и часовой пояс. Расхождение постоянных параметров блокирует
выполнение. Canvas и аудио измеряются и сравниваются между запусками одинаковой
версии движка. В карточке показаны источник, паспорт, результаты и ограничения.
Батарея вынесена в динамическое состояние сессии (`runtime.battery`), отдельно от
паспорта. Эмуляция разряда и зарядки меняется по времени; один сохранённый цикл
используется на всех страницах и при следующих запусках. В карточке показан снимок
на момент последней проверки. Батарея не является телеметрией реального устройства,
не входит в ID отпечатка и не участвует в проверке готовности. Отсутствие Battery API
также не блокирует работу. ID вычисляется только из постоянных параметров, заголовков,
часового пояса, canvas seed и идентификатора профиля; метаданные провайдера исключены.

Старые файлы с батареей внутри fingerprint читаются без регенерации устройства или
потери cookies и хранилищ. При успешном сохранении батарея переносится в runtime.
После остановки исполнителей и резервного копирования БД нормализация существующих
паспортов: `node --env-file=.env scripts/normalize-device-identity.mjs --apply`.
Без `--apply` скрипт только показывает количество изменений. ID существующих
отпечатков однократно меняется из-за новой формулы; затем заряд на него не влияет.

Аудио-хеш MobileProxy сохраняется как справочное значение и не выдаётся за
фактический аудио-результат. Используется измеренный браузером хеш. Шрифты также
проверяются по фактическим метрикам; отсутствующие дают предупреждение. На сервере
установлены Roboto и Noto. Полная эмуляция физического GPU, аудиоустройства или iOS
не заявляется; исходящий TCP/TLS стек этим обновлением не изменяется.

Проверки: `pnpm test:fingerprint`, `pnpm test:pool`, `pnpm test:worker`,
авторизационные и API-тесты на отдельной локальной базе.

## Сессии и диагностика готовности

В разделе «Профили» три вкладки: «Профили и прогрев», «Сайты для прогрева» и
«Настройки». Список сайтов и формы настройки не занимают основной экран очереди.
В настройках число потоков (1–10) задаёт общий предел фоновых запусков. По умолчанию
несколько профилей могут одновременно работать через один прокси; этот режим
можно выключить. Браузеры и хранилища каждого профиля изолированы.

Сервис балансирует прогревы по каналам. Перед первой сессией общей группы канал
меняет IP, если у него настроена ротация; остальные ждут подготовки и используют
тот же IP. Пока хотя бы один профиль группы активен, сервис не выполняет повторную
смену IP этого канала. После освобождения всей группы следующий запуск снова
подготавливает канал. Это касается ротации из Orbit, а не внешнего расписания
провайдера. Идентичные rotation URL и явные алиасы каналов учитываются. Основные
задачи сохраняют эксклюзивный доступ; ожидающая основная задача останавливает
добавление новых прогревов на общий канал, чтобы дождаться его освобождения.

Очередь выбирает три уже начатых прогрева с наступившим сроком этапов 2–4, затем
один первый этап, если обе группы ожидают. Новые профили не вытесняют продолжения,
и продолжения не блокируют новые навсегда. Будущие интервалы не сокращаются.

Журнал в карточке профиля хранится в `ProfileWarmupEvent`: этапы, попытки, канал,
посещения/пропуски сайтов, результаты проверок, сохранение сессии, ошибки и время
следующего запуска. Загрузка постраничная, с автоматическим обновлением. Пароли,
ключи, rotation URL и значения cookies/хранилищ в журнал не попадают. Запись
«Журнал включён» обозначает начало истории существующих профилей; прошлые события
не реконструируются. Миграция `20261005100000_warmup_parallel_journal` добавляет
таблицу и настройку, сохраняя прогресс, параметры устройств и историю проектов.

Приватный файл профиля сохраняет cookies (включая session cookies и разделённые
cookies Chromium), localStorage и IndexedDB: схемы, индексы и записи. Формат
остаётся version 2; старые файлы без IndexedDB читаются без изменения отпечатка.
IndexedDB начнёт сохраняться при следующем успешном запуске. Размер файла ограничен
50 МБ по умолчанию (WORKER_MAX_PROFILE_BYTES), публикация остаётся атомарной и выполняется только при успешном этапе.
Проверено восстановление JSON-значений, дат и типизированных бинарных массивов.
Стандартный экспорт Playwright не гарантирует точный перенос Map/Set внутри
записей IndexedDB. Это снимок поддерживаемых хранилищ, а не полная копия каталога
браузера: sessionStorage и кеш service workers не переносятся.

На этапах 3 и 4 восстановление проверяется в свежем браузерном контексте до
посещения сайтов. Истёкшие cookies не импортируются и не считаются потерянными;
session cookies сохраняются между запусками. Для остальных cookies сравниваются
значения, атрибуты и ключ разделения; для localStorage и IndexedDB — сохранённые
значения и схемы. Пустая сессия, в которой нет действующих cookies, записей
localStorage или IndexedDB, не проходит проверку. Пустое состояние после финального
этапа также не переводит профиль в готовые.

Profile.sessionCheck содержит только результат, время, счётчики и безопасный код
ошибки. Карточка профиля показывает четыре критерия готовности, число действующих
и истёкших cookies, данные хранилищ и время последнего восстановления. Значения
cookies и содержимое хранилищ через API не возвращаются. У ранее прогретых профилей
без sessionCheck результат отображается как неподтверждённый; повторный прогрев
запишет его. Настройки, история использования и старые сессии сохраняются.

Сравнение IndexedDB учитывает данные и типы после декодирования: Playwright может
представить одну и ту же запись как `value` или `valueEncoded` в разных запусках.
Различие этих форматов само по себе не считается потерей данных.

При ошибке прокси прогрев ожидает восстановления канала, не расходуя три попытки
профиля и сохраняя уже пройденные этапы. Канал временно исключается на 60 секунд;
другие независимые каналы продолжают работу. Реальные ошибки профиля по-прежнему
имеют ограничение в три попытки. MobileProxy-ротация запрашивает JSON-ответ и
проверяет `status=OK`; ссылки на смену IP должны совпадать с актуальными
`proxy_change_ip_url` из API провайдера. TLS-проверка остаётся включённой.

Для обхода сайтов выбирается до двенадцати кандидатов из настроенного списка.
Учитываются результаты последних суток на том же прокси: сначала выбираются
сайты с успешными посещениями и один ещё не проверенный сайт. Недавние ошибки
отодвигают сайт в конец списка на 15 минут; адреса за пределами настроенного
списка не добавляются. Недоступный сайт заменяется следующим, но успешный этап
по-прежнему требует посещения трёх разных сайтов. Если доступных сайтов
недостаточно, назначается автоматический повтор через 15 минут без расходования
попыток профиля. Завершённые этапы и прежний снимок сессии сохраняются.
Пропуски, причины и следующий запуск видны в журнале без значений cookies,
паролей и ключей. Ошибки сессии и отпечатка сохраняют ограничение в три попытки.

## Ресурсы сервиса

На странице `/settings/` блок «Ресурсы сервиса» показывает занятый объём файлов Orbit, свободное место на файловой системе, память и CPU процессов приложения, исполнителей и их браузеров. Таблица разделяет приложение с сохранёнными релизами, профили, резервные копии, Chromium, данные исполнителей, базу с прочими данными и журналы служб. Текущий релиз уже входит в общий объём. Файлы измеряются по занятым блокам диска; символические ссылки на каталоги не обходятся повторно.

Данные доступны только после входа через `/api/system/resources/`. Размер файлов обновляется раз в пять минут, сведения о процессах — при запросе с кешем 15 секунд; открытая страница опрашивает их каждые 30 секунд. Параллельные запросы разделяют одну проверку. Память рассчитывается по PSS, а при недоступности PSS используется сумма RSS с пояснением в интерфейсе. CPU показан в занятых ядрах за короткий интервал. Недоступные измерения не подменяются нулём. Каталоги можно задать через `ORBIT_SERVICE_DIRECTORY`, `ORBIT_DATA_DIRECTORY`, `ORBIT_LOG_DIRECTORY`; в стандартном развёртывании они определяются из пути релиза, SQLite и каталога журналов Supervisor.

## Управление сохранёнными релизами

В настройках блок «Сохранённые релизы» показывает дату сохранения каталога (или дату изменения, если время создания недоступно), размер на диске и статус использования. Можно выбрать несколько доступных версий и удалить их после подтверждения. Текущий релиз, версии с работающими процессами, каталоги с настроенными данными и подготавливаемые версии защищены. Сервер повторяет проверки перед удалением; устаревший выбор отклоняется.

Очистка выполняется в фоне, её прогресс виден на странице. Операции записываются в `.release-deletions` внутри папки сервиса. После прерывания подготовка возвращает перемещённые каталоги, а принятая очистка продолжается при следующем запросе списка. При ошибке доступна кнопка «Повторить очистку». Символические ссылки внутри версии удаляются без обхода их целей. После завершения сбрасывается кеш дисковых метрик.

(65% light / 35% dark), ru-RU получает английский fallback, GREASE вычисляется

## Файловый менеджер — 2026-10-20

Раздел `/files/` доступен владельцу через пункт «Файлы» в боковом меню.
Менеджер показывает каталог текущего приложения: папки, скрытые файлы,
размеры и даты; поиск по имени действует внутри выбранной папки, список
постраничный. Файлы скачиваются потоково как вложения без исполнения в браузере.
Кнопка «Скачать папку ZIP» скачивает текущую папку целиком (в корне —
`project.zip`); у каждой папки в списке также есть кнопка ZIP. Архив включает
подпапки, пустые каталоги, скрытые и двоичные файлы. Поиск и пагинация не
ограничивают его содержимое; берутся сохранённые файлы, а не черновик редактора.
Симлинки, специальные файлы, приватная история и временные `.orbit-edit-*`
исключены. Обычные файлы `.next`/`node_modules` включаются, если эти каталоги
находятся внутри выбранной папки; внешние данные по ссылкам не архивируются.
ZIP создаётся потоком через `yazl` 3.3.1 (с автоматическим ZIP64), без временного
архива на сервере. Остановка загрузки освобождает файловые дескрипторы.
Если файл изменился во время чтения или чтение не удалось, скачивание прерывается.
Это выгрузка файлов, а не атомарный снимок работающего приложения.
Текст UTF-8 до 512 КиБ можно редактировать, сохранить через кнопку или Ctrl/Cmd+S.
При конфликте с внешним изменением сохранение отклоняется, черновик остаётся
в редакторе и доступен для отдельного скачивания.

«Загрузить файлы» позволяет выбрать до 20 готовых файлов и отправить их в
открытую папку, до 20 МиБ каждый. Поддерживаются произвольные двоичные данные,
исходная кодировка, BOM и пустые файлы. Перед отправкой показаны новые файлы и
замены; замена подтверждается для конкретной версии. Предыдущие версии
сохраняются в истории. Новый файл получает mode 0600, заменённый сохраняет mode.
API принимает поток `PUT /api/system/files/?path=...&revision=...` с
`Content-Type: application/octet-stream`; revision отсутствует для нового файла.
Лимит проверяется и по Content-Length, и при чтении потока. Прерванная загрузка
не публикует частичный файл; операции пакета последовательные, успешные файлы
сохраняются, а при ошибке интерфейс сообщает, сколько отправлено.
Файловый API исключён из промежуточного Next proxy, чтобы его стандартный
буфер 10 МиБ не обрезал данные; все методы API сами проверяют сессию владельца,
а записи — Origin. В reverse proxy лимит 20 МиБ задаётся только для
`/api/system/files/` (шаблоны Apache/nginx в `deploy/`).

Перед сохранением и удалением создаётся приватная копия. «Корзина и версии»
позволяет восстановить файл или окончательно удалить отдельную копию.
Восстановление поверх существующего файла требует подтверждения и сохраняет
его прежнюю версию. Данные редактора не записываются в localStorage.
Изменение исходников не запускает сборку/перезапуск: интерфейс требует обычной
выкладки, модули воркера — перезапуска соответствующего процесса.

Корень по умолчанию — `process.cwd()`; можно задать `ORBIT_FILES_ROOT`.
Копии находятся в `${ORBIT_DATA_DIRECTORY}/file-manager`, а при отсутствии
переменной — в `.orbit-runtime/file-manager`; явная настройка:
`ORBIT_FILES_HISTORY_DIRECTORY`. На сервере с симлинком `.orbit-runtime`
копии остаются в приватном runtime-каталоге вне web-root. Не размещать их
в `public`. История привязана к физическому каталогу релиза.

Менеджер не следует по символическим ссылкам (включая серверные `.env` и
`.orbit-runtime`), не удаляет папки рекурсивно; `.git`, `.next`, `node_modules`
и `.orbit-runtime` защищены от изменения. Обычные файлы исходников можно
редактировать и удалять; бинарные/большие файлы — скачивать, заменять загрузкой
в пределах её лимита и удалять.
Жёсткие ссылки защищены от изменения. Обход путей блокируется, каждый каталог
открывается через fd с `O_NOFOLLOW`; записи атомарные, с проверкой версии,
сохранением mode и общим межпроцессным замком. API проверяет сессию владельца
для всех операций и Origin для изменений.

Проверки: `node tests/project-files.test.mjs`; после `next build --webpack` —
`node tests/project-files-api.test.mjs` (изолированная SQLite, временные файлы
и Chromium, без обращений к рабочей БД). ZIP проверяется независимым читателем
`zipfile` из стандартной библиотеки Python 3, включая CRC и извлечённые байты.

### Резервные копии файлов сервиса

Настройки → Резервные копии: создание, скачивание `.tar.gz`, важные копии, интервал 1–720 часов и хранение 1–3650 дней. По умолчанию расписание выключено, интервал 24 часа, хранение 7 дней. Очистка применяется и к ручным копиям; важные защищены до снятия отметки.

Копируются исходники приложения/воркеров, миграции, тесты, статические ресурсы и конфигурация сборки. Профили, БД, логи, `.env`, `node_modules`, `.next` и внешние симлинки исключены. Это копия версии кода, а не резервная копия данных или настроек доступа. Архив можно скачать; загрузка произвольных архивов в восстановление не поддерживается.

Восстановление требует остановленных исполнителей проектов и отсутствия активного прогрева. Проверяются SHA-256 и совпадение `prisma/schema.prisma` с текущей версией. Зависимости устанавливаются по сохранённому lock-файлу (`--prefer-offline --frozen-lockfile`) с приоритетом локального pnpm-кеша; недостающие пакеты скачиваются с проверкой целостности. Затем выполняются сборка и проверка запуска. Ошибка установки или сборки оставляет рабочую версию прежней. Миграции БД не выполняются. Перед атомарным переключением `current` создаётся важная копия текущих файлов; при неуспешной проверке веб-сервиса ссылка возвращается назад. Секретные настройки, профили, журналы и БД остаются текущими. После переключения веб-панель и служба прогрева перезапускаются штатным supervisor; проекты остаются остановленными, их запускает оператор.

Хранилище: `ORBIT_SERVICE_BACKUPS_DIRECTORY` либо `<каталог данных>/service-backups`. Независимый от релизов агент устанавливается `node --env-file=.env scripts/install-service-backup-agent.cjs`; его `agent/scripts/service-backups.cjs tick` вызывается раз в минуту из cron от пользователя сервиса, с рабочим каталогом `/var/www/orbit/current` и текущим env-файлом. Само создание выполняется в отдельном процессе, закрытие страницы его не отменяет. Одна операция одновременно; служебный журнал восстановления — `restore-build.log` в каталоге копий. Восстановление старого кода не заменяет установленный агент автоматически.
