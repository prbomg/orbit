# Автономный browser worker

## Версионированный допуск и восстановление сохранения

Допуск требует `readinessVersion = 1`, непустой `snapshotId` и успешного отчёта
о восстановлении именно этого снимка в отдельном процессе Chromium. Отчёт
содержит версию проверки, фактическую версию Chromium, хеш паспорта и время
сохранения. Отсутствие этих полей у старого профиля означает необходимость
повторной аттестации. Паспорт, сохранённые данные и дата завершения подготовки
при этом сохраняются. Фоновая проверка ставит до 100 подготовленных профилей
за проход; уже поставленные в очередь записи не задерживают следующие партии.
Пауза профиля и исчерпанный лимит попыток автоматически не сбрасываются.
Выключенный прогрев и его расписание действуют также для повторной аттестации.

Публикация сеанса использует приватный журнал
`profiles/.publications/<profileId>/`. До замены файлов на диск синхронизируются
новый JSON, исходный JSON, манифест и новый каталог Chromium. Исходный каталог
сохраняется до решения SQL-транзакции. После коммита `Profile.snapshotId`
определяет окончательную версию: новый идентификатор завершает публикацию и
ротацию `.previous`; прежний идентификатор возвращает исходные файлы. Счётчики
и этапы повторно не применяются. Восстановление идемпотентно, включая прерывание
самого восстановления. Ручное восстановление резервной копии использует тот же
протокол и выдаёт снимку новый идентификатор.

Оба исполнителя проверяют журналы при старте; прогрев повторяет проверку раз
в минуту, а сеанс — перед чтением профиля и при завершении. Чужая действующая
аренда профиля блокирует восстановление. При конфликте версии или повреждении
журнала допуск снимается, данные журнала сохраняются для диагностики. Не удаляйте
`.publications` вручную: это часть состояния сервиса, необходимая для отката
незавершённого сохранения. Резервные копии нужно делать после остановки
исполнителей либо согласованным снимком БД и всего каталога профилей.

Проверки прерывают отдельный процесс на границах публикации и SQL-коммита:
`node --test tests/profile-publication.test.mjs tests/profile-attestation.test.mjs`.

## Проверка внешнего IP задачи

Перед посещением сайта worker открывает диагностическую вкладку в том же
BrowserContext, где выполняется задача, и определяет внешний IP через настроенный
IP-endpoint. Production-шаблон использует собственный `/_orbit/ip/`.
Вкладка закрывается до установки ограничений навигации и запуска live-видео.
Запрос из Node.js отдельно определяет адрес исполнителя для сравнения.

В live-журнале появляются `proxy_ip_observed` с `browserIp`, `workerIp`,
`previousIp`, `proxyHost`, `proxyPort`, `ipComparison` и `routeComparison`.
`previousIp` — предыдущее успешное измерение этого proxyId в данном процессе
worker; после перезапуска сравнение начинается заново. Пароли, логины и
ссылки смены адреса не записываются. Те же поля доступны в журнале прогрева.

Совпадение адресов браузера и исполнителя — повод проверить маршрут,
но не доказательство обхода прокси: оба могут иметь общий внешний адрес.
Одинаковый IP между параллельными сессиями общего прокси ожидаем: смена
вызывается один раз перед группой, новые сессии могут присоединяться к ней.
`proxy_rotation_completed` означает успешное завершение запроса смены и
ожидания, а не измеренное изменение адреса.

Настройки:

- `WORKER_PROXY_IP_CHECK_MODE=warn` (по умолчанию): неуспех измерения виден
  в журнале, сценарий продолжает работу. `required` останавливает эту сессию,
  если IP браузера определить нельзя; совпадение IP само по себе не ошибка.
  `off` отключает измерение.
- `WORKER_PROXY_IP_CHECK_URL=https://orbit.server-uniofweb.ru/_orbit/ip/`: HTTPS-сервис,
  возвращающий `{"ip":"адрес"}` или адрес текстом. HTTP разрешён только для
  локальных тестов. Ответ проверяется как IPv4/IPv6. Один дополнительный
  запрос выполняется из браузера и один из Node на каждую сессию.
- `WORKER_PROXY_IP_CHECK_TIMEOUT_MS=5000`: предел каждого измерения.

Собственный endpoint обслуживается веб-сервером без обращения к Next.js или БД,
возвращает только IP клиента и запрещает кэширование. В топологии с внешним TLS
прокси Apache использует `REMOTE_ADDR` после `mod_remoteip`; доверять можно только
проверенным адресам edge, который перезаписывает или корректно дополняет XFF.
PHP-код не читает заголовки, присланные клиентом. До переключения необходима
проверка с поддельными X-Forwarded-For/Forwarded/X-Real-IP и через реальный прокси.
При непосредственном TLS на nginx используется его `$remote_addr`.
Старые установки без WORKER_PROXY_IP_CHECK_URL сохраняют прежний fallback ipify.
WORKER_DIRECT_IP_CHECK_URL позволяет отдельно задать URL сравнения IP исполнителя.
По умолчанию он совпадает с браузерным. На текущем production origin нет обратного
доступа к своему публичному TLS endpoint; поэтому только прямое сравнение Node.js
сохраняет ipify. Его недоступность даёт worker_unknown и не отменяет успешное
измерение браузера. После исправления маршрута edge этот override можно удалить.
Проверка Node.js по-прежнему обозначает только внешний IP исполнителя; она не
заменяет измерение Chromium. HEAD без специального заголовка с адресом не позволяет
узнать IP: production-клиент использует GET с небольшим JSON-ответом.

Проверка настроенных активных прокси отдельно от задач:

```bash
pnpm proxy:check
pnpm proxy:check --all
pnpm proxy:check --proxy=ID
```

Без аргументов выводится список ID/адресов и наличие ссылки смены IP.
С аргументами запускается временный Chromium через выбранный прокси.
База открывается read-only; смена IP, задачи и сохранение профилей не
выполняются. Запускать из текущего релиза с его `.env` и доступом к базе.
Проверка в реальной задаче остаётся более точным подтверждением её маршрута,
чем отдельный диагностический запуск.

Worker читает SQLite напрямую через Prisma; Next.js-сервер для его работы не нужен. База и сгенерированный Prisma Client должны быть подготовлены заранее.

## Подготовка и запуск

Из корня `automation-dashboard`:

```bash
pnpm install
# Если .env ещё не создан:
cp .env.example .env
pnpm db:setup
pnpm worker:install
pnpm worker
```

Если `.env` уже настроен, не перезаписывайте его. Worker сам загружает `.env` из корня приложения и преобразует относительный SQLite-путь относительно папки `prisma`, поэтому его можно запускать из любой папки:

```bash
node /absolute/path/automation-dashboard/worker/index.js
```

Для одной попытки:

```bash
pnpm worker:once
```

`Ctrl+C` или `SIGTERM` останавливает worker и закрывает браузер. Запускать постоянный worker нужно отдельным процессом от Next.js.

## Что выполняется

1. Выбирается задача с `status = "running"` и незакрытым планом. Для каждого сеанса резервируется отдельный готовый профиль, ещё не использованный в проекте. Одновременно резервируется не больше `Task.concurrency` профилей и не больше остатка плана. Если готовых профилей нет, задача ждёт и продолжает работу, когда они появятся. Приоритет — наименьший `currentExecutions`, затем самая ранняя `createdAt`. Автономный worker читает `Task.taskType` из SQLite; BullMQ в проекте не используется.
2. Выбирается включённый прокси (`isActive = true`) с учётом текущей нагрузки. По умолчанию используются HTTP-прокси с авторизацией. Если суммарная параллельность задач проекта не превышает число активных независимых целевых прокси, каждый сеанс проекта резервирует отдельный прокси. Занятый альтернативный канал приводит к ожиданию, а не к повторному использованию прокси проекта. При нехватке прокси нагрузка распределяется до совместного использования. Среди свободных прокси первыми выбираются те, которые дольше не использовались. Разные порты одного хоста считаются отдельными каналами; явный `channel`, одинаковый `rotationUrl` или общий `tcpChannelId` объединяют реальные алиасы.
3. Для `target` с прямым URL по умолчанию генерируется локальный план из 10–15 действий. Он проверяется той же Zod-схемой и не требует API-ключа или сети для генерации. При явном `WORKER_PLAN_MODE=openai` сохраняется прежний запрос к `gpt-4o-mini`; ошибка OpenAI не подменяется локальным планом. Поисковый сценарий и `warmup` всегда используют собственную логику.
4. Если у прокси задан `rotationUrl`, перед запуском группы сеансов выполняется один GET по этому адресу и выдерживается пауза 15 секунд. Новые участники группы используют подготовленный канал без повторной смены IP. При сетевой ошибке, редиректе или ответе вне 2xx браузер не запускается. HTTP 2xx означает принятие запроса провайдером, а не подтверждение нового IP; после паузы соединение проверяется обычным контрольным переходом.
5. Запускается Chromium через `playwright-extra`, подключается `puppeteer-extra-plugin-stealth`.
6. По `TaskExecution.profileId` загружается сохранённый профиль. Существующий `profiles/{profileId}.json` передаётся в `browser.newContext({ storageState: path })`. `fingerprint-injector` внедряет отпечаток до первой страницы. Viewport, Screen, touch, User-Agent и Client Hints согласованы с профилем; пересекающиеся подмены stealth отключены. Cookies и localStorage восстанавливаются до первого перехода.
7. Через тот же браузер и прокси открывается контрольный URL. Если он недоступен, посещение задачи не выполняется, прокси получает временную паузу в памяти worker.
8. Для `warmup` выполняется `performWarmup` по маршруту ниже. Для `target` с поисковыми полями сначала вызывается `performSearchAndClick`; прежние задачи открывают URL напрямую. Если страница содержит поддерживаемую капчу, запускается её обработка, в том числе для страницы с HTTP 403. Ответ вне 2xx без распознанной капчи считается ошибкой.
9. Для прямого URL `executeActionPlan` последовательно выполняет действия из массива, сохраняя их порядок и параметры. Мышь движется по кривым Безье. Случайный клик выбирает видимую обычную ссылку на том же origin; ссылки на скачивание, рекламу, известные операции удаления/выхода/оплаты, ссылки с inline-обработчиками и новые вкладки исключаются. При отсутствии подходящих ссылок действие отмечается как `action_skipped`. Переходы главной страницы на другой origin и навигационные POST блокируются; единственное исключение — одно подтверждённое отправление формы капчи на тот же origin. Внешние iframe разрешены для загрузки виджетов. Фильтр ссылок не определяет назначение всех обработчиков конкретного сайта.
10. В режиме прямого URL, если план закончился раньше выбранного времени 60–120 секунд, worker только ждёт оставшееся время, проверяя статус задачи и появление капчи; дополнительные действия не придумываются. Действия не обрезаются ради выбранного времени. Таймаут поведения — `WORKER_MAX_DWELL_MS` плюс 1 секунда для накладных расходов; превышение означает ошибку. Ожидание ротации и обработка капчи не входят в этот бюджет и могут увеличить общую длительность сессии. После успешного плана, пока контекст ещё открыт, вызывается `context.storageState({ path: temporaryPath })`, затем закрываются контекст и браузер. Если задача всё ещё активна и её `profileId` не изменился, сохраняется профиль и `currentExecutions` атомарно увеличивается на 1.

Счётчик не увеличивается при ошибке, закрытии страницы, остановке процесса, паузе или удалении задачи. Статус задачи/профиля, `profileId` и `taskType` перепроверяются между действиями и во время пауз. Задачи с прямым URL продолжают выполняться до остановки; лимита выполнений нет. Поисковые задачи и прогрев после успеха получают `completed` и больше не выбираются.

`targetKeywords` сохраняются в модели, но не используются как поисковая фраза: для них есть `searchQueries`. Локальный план формируется случайно в пределах заданных параметров, без отправки URL во внешний AI-сервис. Stealth-плагин и имитация движений не гарантируют прохождение конкретных антифрод-проверок.

Ключ OpenAI из Settings остаётся необязательным. В локальном режиме worker его не читает и не обращается к OpenAI. В явном режиме `openai` сохранённый ключ имеет приоритет, резервный источник — `OPENAI_API_KEY` из окружения. Worker использует встроенный Node.js `fetch` для OpenAI в этом режиме и для ротации прокси.

## Мобильные профили

- Файлы находятся в `profiles/{profileId}.json` относительно корня приложения. Папка исключена из Git; новые файлы создаются с правами `0600`, новая папка — `0700`. Другое расположение задаётся через `WORKER_PROFILES_DIR`; относительный путь также считается от корня приложения.
- `Task.profileId` ссылается на `Profile.id` (UUID). При создании задачи API создаёт новый Profile или связывает существующий. Миграция сохраняет UUID и создаёт записи профилей для прежних задач. Чтобы использовать одну сессию для нескольких задач, укажите одинаковый UUID в поле «Профиль браузера» при создании либо в `profileId` POST/PATCH/PUT `/api/tasks/`. UUID виден в таблице задач; форма подсказывает имена существующих активных профилей. PUT без `profileId` сохраняет текущий профиль. Сам UUID не обязан уже иметь файл: файл появится после первой успешной сессии. Один локальный worker выполняет задачи последовательно.
- JSON версии 2 содержит cookies, localStorage и IndexedDB в формате Playwright storageState, отпечаток, HTTP-заголовки, Android/iOS, постоянный `canvasSeed`, UUID, даты и метаданные снимка. Режим `persistent` дополнительно хранит каталог Chromium. SessionStorage не переносится между запусками.
- Для задач с прежними `profiles/{taskId}.json` worker восстанавливает отпечаток и cookies из старого файла, затем после успеха публикует новый файл по UUID. Старый файл остаётся на месте; при ошибке новый не создаётся.
- Новые паспорта поколения 6 (`local-v7`) используют Canvas и OffscreenCanvas без шума из seed и без обёрток Canvas от Orbit. Старые паспорта сохраняют прежний алгоритм чтения и экспорта. Подмена WebGL vendor/renderer и пяти лимитов каталога остаётся эмуляцией. Uniform-лимиты и точность шейдеров измеряются во всех шести контекстах; это значения установленного Chromium, не подтверждённый дамп физического телефона.
- Android использует согласованные мобильные Client Hints из профиля. У iOS Client Hints отключены в JavaScript и сетевых запросах основной страницы; CDP-сессия остаётся подключённой до закрытия страницы.
- Ошибка или остановка сессии не создаёт новый профиль и не обновляет существующий. Повреждённый либо неподходящий файл вызывает понятную ошибку вместо незаметной смены идентичности. Для явного сброса профиля остановите worker и удалите соответствующий JSON.
- Сохранение выполняется через журнал публикации, описанный выше. После ошибки SQL счётчик откатывается вместе с метаданными; журнал возвращает прежние файлы. После успешного коммита восстановление завершает публикацию новой версии и сохраняет предшествующую резервную копию.
- User-Agent и его версия берутся из набора генератора и сохраняются при повторных запусках. Реальный движок остаётся установленным Chromium: iOS-профиль не превращает его в WebKit или физический iPhone. Подмены не гарантируют неразличимость браузера или прохождение проверки произвольного сайта.

## Нажатия и прокрутка

Общий ввод в `mobile-input.mjs` используется просмотром целевых страниц,
поиском и прогревом. Мобильные нажатия проходят проверки видимости,
доступности и перекрытия Playwright, затем отправляются через CDP как
`touchStart` → выдержка → `touchEnd`. Выдержка имеет лог-нормальное
распределение с медианой 90 мс и σ = 0,48; границы 50–350 мс сохраняют
редкие нажатия дольше 200 мс без перехода в обычный long press. Координатные
нажатия используют ту же выдержку. Отмена во время удержания отправляет
`touchCancel`, чтобы не оставлять палец на экране и не завершать клик.

Свайпы идут по кубической кривой Безье. Две контрольные точки отклонены
в разные стороны от основной линии; их боковой сдвиг ограничен 10 CSS px
и 4% длины жеста. Вся огибающая кривой вместе с радиусом касания проверяется
на перекрытия, карты, карусели и соседние области прокрутки. Для каждого
обычного свайпа отдельно выбирается длительность 800–2000 мс. Профиль
скорости сначала ускоряет, затем замедляет движение; при отпускании остаётся
небольшая скорость. Короткие точные коррекции сохраняют режим 150–320 мс
с полной остановкой. Явная `durationMs` переопределяет длительность, например
в локальных проверках. При задержках CDP устаревшие точки пропускаются.

После `touchEnd` исполнитель дожидается остановки выбранного контейнера
перед следующим свайпом. Нативная инерция Chromium имеет приоритет. Если
успешный свайп не вызвал продолжения движения, `scroll-inertia.mjs` применяет
резервную модель только к этому контейнеру: `v(t) = v0·exp(-t/τ)`,
`D = K·v0²`, `τ = D/|v0|`. Скорость измеряется по последним точкам и их
фактическому времени, в px/s; `K = 0,0008 s²/px`. Дистанция ограничена
длиной безопасного жеста и границами контейнера, расчёт заканчивается через
`5τ` (более 99% дистанции). Нативная инерция не дополняется второй кривой;
её закон затухания задаёт браузер. Заблокированное касание не заменяется
программной прокруткой. Резервная анимация прерывается при отмене задачи,
изменении области или вмешательстве другой анимации.

Проверки модели, событий браузера, вложенных контейнеров и отмены:
`pnpm test:gestures`.

## Прогрев профиля

В форме создания задачи на Dashboard или Tasks выберите «Прогрев профиля». Можно создать новый профиль, оставив UUID пустым, либо выбрать существующий. URL и ключевые слова для прогрева не нужны. В API передайте `taskType: "warmup"` и при необходимости `profileId`.

В разделе «Профили» редактируется список сайтов для прогрева: от 3 до 200 HTTP(S) адресов, минимум три разных домена. Список хранится в `Settings.warmupSites`; пока он не задан, используется исходный список из 20 сайтов в `utils/donorSites.js`. Перед каждым этапом сервис читает актуальные настройки, перезапуск не нужен. `worker/warmup.mjs` выбирает три разных сайта; несколько страниц одного домена не увеличивают вероятность выбора этого домена. В одном контексте на каждом сайте выполняется:

1. Переход и ожидание 3–7 секунд.
2. На каждой новой странице 2–4 последовательных прокрутки вниз по 220–680 px с паузами чтения 1,8–4,2 секунды. С вероятностью 25% после них выполняется один заключительный возврат вверх на 120–280 px. Первый шаг всегда вниз.
3. Один клик по обычной внутренней ссылке текущего origin. После начальных редиректов используется фактический origin страницы. Ссылка может находиться за пределами viewport: Playwright прокрутит её в область клика. Сохраняются исключения для скачивания, inline-обработчиков, новых вкладок и известных действий выхода/покупки/удаления. При отсутствии подходящей ссылки выводится `warmup_link_skipped`.
4. Ожидание 5–10 секунд после клика, либо на той же странице при пропуске ссылки.

Прогрев проходит четыре этапа: два запуска на сайтах из списка, проверка восстановленной сессии и финальная проверка отпечатка. После успешного этапа runner сохраняет cookies/localStorage всех посещённых origin в `profiles/{profileId}.json`. Только четвёртый этап переводит профиль в «Готов»; прогрев не создаёт основных задач. Интервал между этапами задаётся в «Профилях» в часах (можно дробные значения), в базе сохраняется с точностью до минуты. Изменение интервала применяется при планировании следующего этапа; уже назначенный запуск остаётся на своём месте. Ошибка, отмена или пауза отменяет публикацию файла. Ограничение 60–120 секунд относится к задачам прямого URL; длительность прогрева определяется его паузами, переходами и обработкой капчи. Историю посещений Chromium worker не сохраняет: накапливается только storageState, а наличие cookies зависит от самих сайтов.

`Profile.status` поддерживает `new`, `warming_up`, `ready`, `banned`; пауза сохраняется в `isEnabled`; изменить имя/статус можно PATCH `/api/profiles/{id}/`. GET `/api/profiles/` возвращает список, POST создаёт профиль с указанным именем. При удалении задачи профиль и файл сессии сохраняются для повторного использования.

## Поиск и переход

`performSearchAndClick(page, task)` находится в `worker/search.mjs`, вспомогательные функции экспортируются отдельно: `typeTextHumanLike`, `findInSerpOrPaginate`, `visitCompetitors`, `interactWithTargetSite`. Runner сохраняет профиль и закрывает браузер.

Глубина поиска задаётся полем задачи `searchDepth` в интерфейсе и API; миграция сохраняет прежнее значение 5 для существующих задач. Изменение параметра активной задачи обрабатывается так же, как изменение её поисковых фраз.

Поля `searchEngine`, непустой JSON-массив `searchQueries` и домен из `Project.targetUrl` включают существующий поисковый режим; `vitalPhrases` — необязательный JSON-массив уточнений. Каждый список содержит до 100 непустых фраз по 500 символов. API принимает массивы, интерфейс преобразует строки textarea в массивы, удаляя пустые строки и дубликаты. Миграция переносит старую `searchQuery` в массив из одной фразы и удаляет колонку; UUID и существующие сессии сохраняются.

Перед действиями на странице поисковика проверяются видимые модальные окна и предложения установить приложение/назначить поиск по умолчанию. `search-overlays.mjs` ищет доступную кнопку закрытия в окне или его плавающем контейнере (включая отдельный крестик над нижней панелью), нажимает её и ждёт исчезновения окна. Повторные окна закрываются не более трёх раз за проверку. Недоступное закрытие останавливает попытку с `search_overlay_blocked`; события видны в наблюдении. Кнопки согласия, изменения настроек и очистки запроса не используются.

Сценарий:

1. Случайная поисковая фраза вводится посимвольно с задержкой 50–200 мс. Перед отправкой значение поля сверяется с исходной фразой; если автоподсказки съели пробелы, текст восстанавливается. Если адрес выдачи содержит другой запрос, отправка повторяется один раз. Главные поля и iframe поисковой формы поддерживаются; формы отправляются в родительскую страницу. Выдача может измениться через навигацию или AJAX.
2. До `searchDepth` страниц (целое число 1–10, по умолчанию 4) проверяются на точное совпадение домена/поддомена. Переход по «Далее», «Показать ещё», rel=next или номеру страницы. Если на мобильной выдаче продолжения нет, поиск завершается на доступной странице и переходит к витальной фразе при её наличии. Рекламные результаты, опасные пути, непрозрачные tracking-ссылки исключаются.
3. Если цели нет и есть витальные фразы, случайная фраза дописывается к исходному запросу через пробел; выполняется ещё один проход с тем же пределом `searchDepth`. Без витальных фраз второго прохода нет. Отсутствие цели после этих проходов возвращает `found: false` и сохраняет прежние счётчик/профиль.
4. С вероятностью 65% перед целью посещаются 1–2 разных органических домена из первых пяти результатов; цель и её поддомены исключаются. Если доступных доменов меньше, посещаются доступные; если нет — этап пропускается. На каждом задано 10–20 секунд пребывания с 3–4 прокрутками, распределёнными по интервалам чтения 2,5–5 секунд. Время взаимодействий учитывается в длительности; пропущенные из-за медленного действия или проверки капчи интервалы не догоняются серией скроллов. Проверки отмены и капчи сохраняются.
5. Для новой вкладки ожидание popup устанавливается до клика, вкладка закрывается после посещения. При переходе в текущей вкладке используется `goBack()`, проверяются URL и наличие выдачи. После возврата ссылки повторно парсятся, старые DOM-токены не используются.
6. Последний внешний переход — цель. Визит длится 60–300 секунд со скроллами, движениями курсора и переходом по 1–2 доступным внутренним ссылкам. Если безопасных ссылок нет, чтение продолжается. Навигация остаётся внутри целевого домена.
7. Только успешный визит сохраняет cookies/localStorage, увеличивает счётчик и устанавливает `status: completed`. Ошибка, остановка или изменение задачи не публикуют состояние.

Новый поисковый сценарий использует собственный план взаимодействий; OpenAI-план остаётся для старого режима прямого URL. Поэтому поисковые задачи не требуют платного генерационного запроса. HTTP-ошибки и отсутствие обязательных элементов завершают сценарий контролируемой ошибкой; отсутствие кнопки следующей страницы фиксируется как конец доступной выдачи. URL и фразы не печатаются в логах, выводятся этапы, домены и длительности. Общий бюджет решений капчи применяется ко всем вкладкам сессии.

Очереди BullMQ в проекте нет: процесс последовательно обрабатывает задачи, блокировка SQLite-файла удерживается на протяжении всей работы процесса и не истекает после минутного ожидания. `navigationTimeoutMs` ограничивает отдельную навигацию, а не всю сессию. При будущей интеграции BullMQ задайте `lockDuration: 600000` и сохраните автоматическое продление блокировки.

Проверки используют перехваченные локальные страницы: main/iframe поля, AJAX-пагинацию, обычный возврат, popup, уточнение, отсутствие цели, HTTP-ошибки и сохранение storageState. Реальная разметка поисковиков может потребовать обновления адаптеров; успешность антифрод-проверок или влияние на ранжирование не гарантируются. Внутренние переходы и конкуренты выбираются из распознаваемых органических ссылок.

## Ротация и RuCaptcha

- На странице «Прокси» у каждой записи есть скрытое поле URL ротации и кнопка сохранения. Пустое значение отключает ротацию. Также поле `rotationUrl` можно передать в POST/PATCH/PUT `/api/proxies/`. URL должен быть HTTP(S) без встроенной авторизации; ключ провайдера в query-параметрах поддерживается. URL сохраняется в SQLite, возвращается API прокси для редактирования, но не печатается в worker-логах.
- На странице «Настройки» задайте API-ключ RuCaptcha. Он сохраняется в `Settings.rucaptchaApiKey` для записи `id = 1`. GET/PATCH `/api/settings/` возвращает только `{ "rucaptchaConfigured": true/false }`. Для удаления передайте `rucaptchaApiKey: null` или нажмите «Удалить ключ». Worker перечитывает ключ при каждой обнаруженной капче.
- Ключ хранится в SQLite, как и пароли прокси; защитите доступ к файлу базы и локальной панели. Новые миграции применяются командой `pnpm db:setup`, существующие записи сохраняются.
- Для reCAPTCHA используется `2captcha` — npm alias официального `@2captcha/captcha-solver@1.3.9` и API v1. Для Yandex SmartCaptcha запросы отправляются напрямую через API v2 (`createTask` / `getTaskResult`). По умолчанию используются `https://rucaptcha.com` для v1 и `https://api.rucaptcha.com` для v2. Для аккаунта 2Captcha задайте `WORKER_CAPTCHA_BASE_URL=https://2captcha.com` и `WORKER_CAPTCHA_V2_BASE_URL=https://api.2captcha.com`, затем сохраните его ключ в том же поле настроек.
- Проверка выполняется после загрузки задачи, между действиями AI-плана и во время пауз. Поддерживаются reCAPTCHA v2 (также enterprise/invisible при доступных параметрах) и Yandex SmartCaptcha: `data-sitekey`, классы виджетов или известные iframe с ключом в query-параметрах. При отсутствующем sitekey запрос не оплачивается и сессия завершается ошибкой.
- Провайдер получает sitekey, полный URL страницы, User-Agent и данные выбранного прокси, чтобы решение использовало тот же IP. Для SmartCaptcha отправляется одна задача API v2 и опрашивается её результат; автоматических повторов создания задачи внутри решения нет. Уже созданная платная задача может остаться у провайдера после остановки worker. При прямом запуске браузера используется `YandexSmartCaptchaTaskProxyless`.
- Токен записывается в `g-recaptcha-response` или `smart-token`, отправляются события input/change, вызывается явно заданный именованный `data-callback`. Затем нажимается видимая кнопка отправки связанной формы. Формы с паролями и формы на другом origin не отправляются. Ответ формы вне 2xx считается ошибкой. Токен в поле сам по себе не доказывает его принятие сайтом.
- Базовый адаптер рассчитан на обычную форму с навигацией либо явно заданный callback. SPA с AJAX-отправкой, неэкспортированные JS-callback, виджеты с динамической конфигурацией без доступного sitekey, reCAPTCHA v3 и другие виды капчи требуют отдельного адаптера. Успех на произвольном сайте не гарантируется.
- На полноэкранной проверке Яндекса `/showcaptcha` или `/showcaptchafast` обработчик автоматически нажимает чекбокс, затем ждёт до 15 секунд появления sitekey или визуального задания. Для sitekey запрашивается токен RuCaptcha; для основной картинки 320×180 и строки инструкций 480×80 (либо 480×180) создаётся `SmartCaptchaTask`. Строка 480×80 дополняется полями до требуемых API 480×180 без искажения символов, затем полученные координаты нажимаются в браузере. Если ни один поддерживаемый вариант не появился, сессия завершается кодом `widget_not_detected` без платного запроса. Если ключ отсутствует, сессия завершается кодом `missing_api_key`.
- После нажатий воркер ищет кнопку отправки внутри формы изображения, включая `button`/`input` с `type="submit"`, и ждёт её активации. Без формы поддерживаются названия «Далее», «Подтвердить», «Отправить» и другие варианты. Для POST заранее разрешается адрес формы на том же origin, в том числе при автоматической отправке после последней координаты; разрешение очищается после обработки. `submission_rejected` означает, что страница проверки не закрылась после отправки, и также может возникать при неверном решении провайдера.
- Видимый браузер можно использовать для наблюдения. Ожидание ручного решения по умолчанию выключено и включается только явным `WORKER_CAPTCHA_MANUAL_WAIT_MS` больше нуля вместе с `WORKER_HEADLESS=0`.
- Изображения передаются в исходном разрешении, независимо от размера их отображения в мобильном браузере. Если картинка с другого домена блокирует чтение canvas из-за CORS, воркер читает тело исходного HTTP-ответа изображения, уже полученного браузером для текущей страницы. Захват ответов подключается до первой навигации; ссылки на ответы хранятся отдельно для каждого фрейма и очищаются при переходе. Вёрстка не меняется и URL не загружается повторно: повторный запрос может быть запрещён или вернуть другое задание. Байты декодируются напрямую через Blob/createImageBitmap и обрабатываются OffscreenCanvas: не создаётся data URL для загрузки внутри страницы, поэтому запрет img-src data: не мешает обработке, а canvas-профиль не меняет экспортируемые пиксели. Корректные изображения с общим Content-Type application/octet-stream также принимаются. Инструкция затем дополняется полями до размера API. Если получить изображение не удалось, возвращается `image_capture_failed` без запроса в RuCaptcha. При `ERROR_CAPTCHA_UNSOLVABLE` или отклонении координат воркер обновляет страницу проверки и повторяет распознавание в той же сессии. За сессию разрешено до пяти запросов распознавания (`WORKER_CAPTCHA_MAX_SOLVES=5`); отдельно учитываются три некорректных решения (`WORKER_CAPTCHA_MAX_INCORRECT=3`). Успешные решения не расходуют лимит некорректных, а ошибки загрузки и получения изображения не считаются неправильными ответами. После ошибки попытка задачи завершается, её повтор получает другой профиль и прокси. Серия одинаковых ошибок хранится в `Task.retryState`: на пятой останавливается только эта задача, другие задачи проекта продолжаются. Успешное выполнение сбрасывает серию, другая ошибка начинает новую. При нехватке другой пары ресурсов задача ожидает. Ручной повтор задачи после остановки начинает новую серию. Повторы и отдельные нажатия видны в журнале наблюдения.
- Управляемый запуск проекта останавливается при `widget_not_detected`, `sitekey_missing` или `missing_api_key`, чтобы не повторять безрезультатные попытки. Задача остаётся в базе без нового выполнения; после исправления условий проект можно запустить снова.
- Клиент API работает в отдельном дочернем процессе. Таймаут, SIGTERM и пауза/удаление задачи прекращают его опрос, браузер закрывается, счётчик не увеличивается. Лимит платных решений на сессию по умолчанию — 3.

## Диагностика интеграции RuCaptcha

При просмотре сайтов обработчик отличает активную проверку от фонового виджета:
скрытые iframe, `size=invisible` без открытого задания и капчи обычных форм заявки
не запускают решение и не останавливают посещение. Если у invisible reCAPTCHA
открыт видимый iframe задания `bframe`, проверка продолжает распознаваться.
На отдельных страницах `/showcaptcha` и `/showcaptchafast` Яндекса служебные
скрытые виджеты сохраняются в обработке: эти страницы сами блокируют переход.
Содержимое скрытых дочерних фреймов также исключается. Лимит платных решений
остаётся общим для сессии: успешно пройденные проверки учитываются в нём,
а фоновые виджеты — нет. Журнал показывает номер обнаруженной проверки и лимит.

Для проверки получения изображений, API v1/v2, применения координат и безопасного журнала выполните `pnpm test:captcha`. Тесты используют локальный API без платных запросов. Мобильные профили и жизненный цикл процесса дополнительно проверяются в `pnpm test:worker`.

В «Переходы и действия» перед запросом в RuCaptcha появляются две записи: «Основная картинка получена · 320×180» и «Инструкция получена · 480×180». Если их нет, подготовка остановилась до обращения к провайдеру. Перед общей ошибкой `image_capture_failed` выводится отдельная запись с названием изображения и точной стадией:

| Код | Причина |
| --- | --- |
| `browser_image_decode` | Браузер не смог обработать исходный элемент изображения |
| `image_source_read` | Источник элемента недоступен или изменился |
| `original_response_missing` | Для текущего элемента не найден исходный ответ; дополнительные поля показывают тип элемента, схему источника, состояние захвата и число сохранённых ответов |
| `original_response_body` | Тело исходного ответа недоступно, пусто или превышает 5 MB |
| `original_image_decode` | Не удалось декодировать исходные байты или изображение сменилось во время обработки |
| `canvas_snapshot` | Не удалось снять копию нарисованного canvas в исходном размере |

В журнал не передаются исходные URL изображения, содержимое исключений, изображения и API-ключи. Ошибки SDK reCAPTCHA сохраняют строковый код провайдера, например `ERROR_ZERO_BALANCE`, вместо внутреннего номера SDK.

Ответ изображения сопоставляется со всей цепочкой HTTP-перенаправлений; фрагмент `#...` не участвует в сопоставлении. Смена URL через `history` или якорь сохраняет ответы загруженного документа. Очистка выполняется при ответе новой навигации, а не при каждом `framenavigated`; HTTP 204/205 и загрузка файла не сбрасывают ответы текущей страницы. Количество последующих иконок не вытесняет основную картинку. Эти сценарии проверяются настоящими локальными HTTP-ответами в `tests/captcha-image-network.test.mjs`.

Инструкция может быть нарисована в canvas, а не загружена через img. Если canvas содержит картинку с другого origin, браузер запрещает экспорт его пикселей; у самого canvas нет URL. В этом случае воркер копирует уже нарисованный bitmap в пустое окно того же origin, дополняет его до требуемого размера и делает PNG-снимок в масштабе CSS 1:1. Сохраняются дорисованные элементы инструкции. Мобильная страница, её размеры и стили не меняются; временное окно закрывается перед запросом в RuCaptcha, при ошибке и при отмене. HTTP-запрос картинки не повторяется. В успешном событии используется метод `canvas_snapshot`.

При сохранении профиля поддерживаются partitioned cookies Chromium, включая `partitionKey` и `_crHasCrossSiteAncestor`. Состояние браузера сначала получается в памяти, затем проверяется и записывается одним приватным временным файлом. Публикация остаётся атомарной. Ошибка захвата состояния отмечается как `profile_storage_failed`, несовместимые данные — `profile_state_invalid`, отсутствие прав — `profile_permission_denied`, нехватка места — `profile_disk_full`; прочая ошибка записи — `profile_write_failed`. Журнал не содержит значений cookies и исходных исключений. После ошибки профиля управляемый проект останавливается, чтобы не повторять всё посещение с новым решением капчи; последнее успешно сохранённое состояние и счётчик выполнения сохраняются. Некорректный планшетный sample при создании нового мобильного профиля пропускается, старые сохранённые профили не пересоздаются.

`submission_rejected` после POST `/checkcaptcha` и возврата `/showcaptcha` означает, что Яндекс не принял отправленное решение. Это отдельный этап от получения изображения: проверять следует актуальность задания, последовательность нажатий и ответ страницы.

## Формат плана

Массив содержит 10–15 объектов следующих типов:

| Действие | Параметры |
| --- | --- |
| `scroll_down` / `scroll_up` | `pixels`: целое 100–1500 |
| `pause` | `durationMs`: целое 2000–8000 |
| `move_mouse_randomly` | `durationMs`: целое 100–2000 |
| `click_random_link` | Без дополнительных параметров |

Например, элемент массива: `{"type":"scroll_down","pixels":500}`. Суммарный `durationMs` должен быть меньше максимальной длительности сессии. Модель не может передать JavaScript, селектор или произвольный URL для выполнения.

Обход сайтов ограничен этой длительностью плюс одним `WORKER_NAVIGATION_TIMEOUT_MS` на служебные действия.

Журнал прогрева сохраняет фактическое смещение, подтверждение внутренних переходов, операции и принадлежность HTTP-ответа
документу или ещё не подтверждённому переходу. Полные URL, значения cookies и учётные данные не записываются.
События объединяются в небольшие пакеты (до 250 мс / 25 записей). `warmup_database_metrics` содержит время очереди
записи внутри процесса и время транзакций (включая ожидание SQLite); это разные показатели.
Миграция `20261014160000_warmup_journal_indexes` добавляет индексы истории по прокси/времени и событию/времени.
Проверки: `node --test tests/warmup-diagnostics.test.mjs tests/warmup-parallel.test.mjs tests/warmup-recovery.test.mjs`.

При отсутствии активных задач или включённых прокси worker ждёт. В режиме `--once` он выводит `waiting` и завершает работу без запуска браузера. Включённый прокси не считается заведомо доступным: проверка соединения проводится перед каждой попыткой. Контрольный URL не определяет тип IP и не подтверждает работоспособность прокси для всех сайтов.

## Ошибки, блокировка и логирование

- Для каждого проекта работает отдельный worker. Его блокировка: `<database>.workers/<projectId>.lock`, состояние и журнал: `.orbit-runtime/projects/<projectId>/worker.json` и `worker.log`. Несколько проектов запускаются одновременно; повторный запуск уже работающего проекта отклоняется.
- Общий CLI-worker без `--project` сохраняет эксклюзивную блокировку `<database>.worker.lock` и не запускается одновременно с исполнителями проектов. Прогрев имеет собственную блокировку.
- Статусы и наблюдение разделены по проектам. API `/api/system/` возвращает `projectRuns` и `activeProjectCount`; поле `projectRun` оставлено для случая одного активного проекта. Старые записи состояния читаются только для соответствующего проекта.
- Профили, прокси, суточные резервы и лимиты потоков распределяются транзакциями общей БД. Каждый исполнитель хранит отдельную заявку на свободный канал; остановка одного не стирает заявки других. При нехватке ресурсов проекты ожидают.
- Блокировка освобождается при нормальной остановке. Блокировка завершившегося процесса восстанавливается при следующем запуске. Это локальная защита, не распределённая очередь.
- Ошибка контрольного перехода ставит выбранный прокси на временную паузу; ошибка целевого сайта — задачу. `isActive` и `status` в базе при этом не меняются.
- Ошибка ротации ставит прокси на паузу; ошибка капчи — задачу. Таймауты и ошибки не увеличивают счётчик.
- В локальном режиме ошибок OpenAI нет. В явном режиме `openai` ошибка API ставит внешние запросы на паузу `WORKER_COOLDOWN_MS`; при запуске проекта ответы 401, 403 и 429 завершают исполнителя с кодом ошибки. Некорректный план ставит задачу на временную паузу в памяти worker.
- Логи — JSON с типом события и идентификаторами. Пароли, логины прокси, полный URL и необработанные исключения браузера не печатаются.
- События `plan_requested`, `plan_ready`, `action_started`, `action_completed`, `action_skipped`, `action_failed`, `session_wait` показывают текущий этап. Каждое действие содержит `step`, `total`, `action` и числовые параметры. Например: `{"event":"action_started","step":5,"total":10,"action":"pause","durationMs":4000}`.
- Для внешних сервисов добавлены `proxy_rotation_started/wait/completed` и `captcha_checkbox_clicked/detected/requested/token_received/token_applied/coordinates_received/coordinates_applied/callback_invoked/submitting/submitted/failed`. Если callback сам отправляет форму, повторного нажатия кнопки нет. В логах нет ключей, URL ротации, токенов, sitekey, изображений или содержимого ответов провайдера.
- События `profile_generated`, `profile_loaded`, `profile_saved` показывают создание, повторное использование и сохранение профиля. Логи содержат UUID, тип ОС и количество cookies, без их значений, localStorage и самого отпечатка.
- `warmup_started/site_started/wait/scroll/link_clicked/link_skipped/site_completed/completed` показывают прогрев. Начало сайта содержит домен; полные адреса страниц и содержимое сессии не печатаются.
- Атомарный SQL increment защищает счётчик от потери параллельных изменений. Если процесс аварийно завершится между закрытием браузера и обновлением базы, посещение не будет учтено.
- Данные открытой панели обновляются каждые пять секунд на видимой вкладке; доступно ручное обновление. История запусков и дневная статистика пока не сохраняются.

## Проверка

```bash
pnpm test:worker
```

Тесты используют временную SQLite-базу, локальные страницы, HTTP-прокси с авторизацией и имитации OpenAI/RuCaptcha. Настоящий Chromium проверяет порядок действий, 15-секундную ротацию до первого браузерного запроса, извлечение ключа из iframe reCAPTCHA, заполнение скрытых полей обоих типов капчи и POST формы. Проверяются появление SmartCaptcha после действия, пауза бюджета поведения во время решения, ошибки ротации/провайдера, отсутствие ключей, таймауты, SIGTERM и счётчики. Время поведения сокращено; рабочие задачи и прокси не затрагиваются. Настоящие платные API и мобильный провайдер этими тестами не вызываются.

Проверки профилей запускают отдельно Android и iOS: значения доступны первому скрипту документа, User-Agent/Client Hints соответствуют профилю в HTTP и JavaScript, Canvas стабилен при повторном чтении: у новых Android-паспортов совпадает с нативным выводом, у прежних iOS-паспортов сохраняет прежний результат. Проверяется сохранение cookies, localStorage и отпечатка между сессиями, наличие localStorage уже в первом скрипте нового документа, неизменность файла после ошибки, права доступа, отклонение повреждённых профилей и чтение старого формата. API-тесты проверяют автоматические UUID и возможность совместного использования профиля.

Прогрев проверяется на трёх локальных HTTP-origin с настоящим Chromium: внутренние клики, диапазоны пауз и скроллов, cookies/localStorage всех origin, отсутствие OpenAI, однократное сохранение и завершение задачи. Также проверяются ошибка сайта, отмена, пауза профиля и сохранность UUID/полей при миграции. Настоящие сайты-доноры тесты не посещают.

Поиск проверяется на перехваченных локальных страницах: основной/iframe ввод, Enter, пять страниц, organic/advertising фильтр, lookalike-домены, readable tracking-ссылки и target=_blank. Интеграция runner проверяет успешное сохранение цели и закрытие браузера без изменения последней сессии/счётчика при отсутствии цели.

API библиотек: [playwright-extra](https://github.com/berstend/puppeteer-extra/tree/master/packages/playwright-extra), [stealth plugin](https://github.com/berstend/puppeteer-extra/tree/master/packages/puppeteer-extra-plugin-stealth), [Playwright proxy](https://playwright.dev/docs/network#http-proxy).

Отпечатки: [Fingerprint Suite](https://github.com/apify/fingerprint-suite), [Chromium User-Agent override](https://chromedevtools.github.io/devtools-protocol/tot/Network/#method-setUserAgentOverride).

Персистентные сессии: [Playwright storageState](https://playwright.dev/docs/auth).

OpenAI Docs: [Chat Completions API](https://developers.openai.com/api/reference/resources/chat), [gpt-4o-mini](https://developers.openai.com/api/docs/models/gpt-4o-mini).

Документация провайдера: [официальный JavaScript SDK](https://github.com/2captcha/2captcha-javascript), [API RuCaptcha/2Captcha](https://2captcha.com/ru/2captcha-api).

## Учёт проекта и прогресса

После изменения схемы исполнитель читает связь `Task.project` и получает целевой домен из адреса проекта. Успех учитывается через `utils/taskLifecycle.js`: `currentExecutions` увеличивается, целевое выполнение добавляется в `ProfileProjectHistory`, успешный прогрев увеличивает `warmupScore`. `targetExecutions` задаёт верхнюю границу; выключенный или заблокированный профиль не исполняется.

Браузерные действия и их порядок в этом обновлении не менялись. Существующие поисковые сценарии и прогрев завершаются после одного успешного сценария; если план поисковой задачи ещё не исчерпан, её можно снова поставить в очередь вручную. Новая система автоматического распределения профилей по числу выполнений не добавлена.

## Недельное расписание прогрева

На странице «Профили → Настройки → Расписание прогрева профилей» выбираются часы недели и часовой пояс независимо от расписаний проектов. Кнопка «Ежедневно ночью» выбирает 20:00–08:00 каждого дня. По умолчанию разрешены все 168 часов. Пустая сетка запрещает новые старты.

Ограничение проверяется при резервировании профиля и прокси, действует на первые этапы, продолжения, повторные попытки и проверки готовности. Активный сеанс завершается даже после закрытия окна; для полного разделения с дневными задачами нужен временной запас между окнами. Общая пауза прогрева и индивидуальные паузы имеют приоритет. Очередь и интервалы этапов сохраняются; окно может увеличить фактический срок подготовки. Изменения применяются без перезапуска службы.

Проверки: `node --test tests/warmup-schedule.test.mjs tests/project-schedule.test.mjs tests/warmup-parallel.test.mjs`. При запуске тестов из production-релиза задайте `WORKER_PROFILES_DIR=""`, чтобы фикстуры не зависели от настоящего каталога профилей. Браузерная/API-проверка `tests/warmup-schedule-ui.test.mjs` требует отдельной локальной базы и сервера.

Выбор поискового запроса балансируется отдельно для каждого задания по подтверждённым переходам за всё время: случайный выбор среди запросов с минимальным числом переходов. Текущие выбранные запросы параллельных `running`-сеансов временно учитываются через `TaskExecution.selectedSearchQuery`; после регистрации перехода сеанс не учитывается повторно. Неуспешные и прерванные сеансы освобождают резерв при смене статуса, повторный запуск сбрасывает выбор. Витальное уточнение засчитывается исходному запросу. Старая история без сохранённого запроса не участвует в балансировке. При ошибках и параллельном исполнении временная разница допустима; последующие выборы компенсируют её.

После ошибки целевой задачи повтор получает другой готовый профиль и другой независимый прокси, включая HTTP 429 и прокси со ссылкой смены IP. Профили с ошибкой исключаются из последующих выполнений этой задачи. Успешное завершение параллельного сеанса не отменяет необходимость заменить ресурсы после ещё не обработанной ошибки. При отсутствии подходящего профиля или другого прокси задача ожидает. Ручная остановка не считается ошибкой.

При HTTP 429 новые сеансы не присоединяются к проблемной группе; действующие сеансы завершаются штатно. Если ссылка смены IP не задана, проблемный канал дополнительно получает паузу минимум 15 минут, затем 30/60/120/240 минут при повторениях, не короче `Retry-After`. Другие каналы продолжают работать. Старое сохранённое правило `rotate_proxy` автоматически заменяется на `replace_proxy` без сброса счётчиков и серии ошибок. После пяти одинаковых ошибок останавливается только это задание; HTTP 429 не засчитывается как выполнение или переход.

## Надёжность профилей и прогрева

Миграция `20261012110000_profile_reliability` добавляет `WarmupSiteHealth`, версию снимка в `Profile` и кеш проверки привязки провайдера в `Proxy`. Существующие паспорта и файлы совместимы; новые метаданные появляются при следующем проверенном сохранении. Перед миграцией остановите обе службы и управляемый исполнитель, сделайте резервную копию SQLite.

Сайты прогрева резервируются через общие leases: до двух посещений домена одновременно, одно на канал. Ошибки сохраняются по домену/каналу; пауза 15/30/60/120/240/480 минут, HTTP 429 блокирует домен на всех каналах и соблюдает Retry-After. После истечения паузы ограничение параллельности допускает контрольный повтор. Автоматическая пауза не отменяет ручное исключение сайта. Состояние и причины видны в настройках сайтов; статистика каналов накопительная.

Паспорта новых профилей содержат версию генератора, набора устройств и адаптера. Противоречивые параметры отклоняются до прогрева. Отсутствующая привязка прокси к MobileProxy кешируется 30 минут и сбрасывается при изменении адреса/логина/канала; режим auto сохраняет причину локального fallback, строгий режим провайдера остаётся строгим.

Каждый новый снимок содержит UUID, хеш содержимого и постоянных параметров. Сессия проверяется после запуска отдельного процесса Chromium до публикации. Для постоянного каталога проверяются его собственные данные; session cookies восстанавливаются отдельно из снимка, остальные cookies не подставляются. Полный импорт снимка разрешён только при первом создании или явно запрошенном переключении хранилища.

Предыдущий JSON сохраняется в `<id>.json.previous`, предыдущий каталог — в `browser-data/<id>/previous`. Очищаются только GPUCache, ShaderCache, GrShaderCache, GraphiteDawnCache и Crashpad. HTTP Cache, Code Cache, Cookies, Network Persistent State, TransportSecurity, Service Worker и CacheStorage сохраняются. Лимит 100 МБ относится к данным вне кеша; бюджет HTTP-кеша Chromium — 50 МБ. Восстановление предыдущего снимка доступно в карточке сессии только для свободного профиля с совпадающим паспортом. Оно снимает готовность и приостанавливает прогрев до проверки/продолжения. Копии содержат cookies: храните их с теми же правами и политикой доступа, что и основные данные.

### Подготовка профилей: проверяемые результаты (2026-10-14)

Новые планы имеют версию 2. `warmupPlanPreset` в настройках выбирает `standard`
(6 сессий, 3 сайта, 3 минуты), `storage` (1 / 1 / 1), `revisit` (2 / 1 / 2)
или `navigation` (2 / 2 / 2). Для двухсессионных планов пауза равна настроенному
интервалу этапов. Существующие планы v1 сохраняются; смена настройки применяется
к новым профилям или явному перезапуску подготовки. Во всех планах сохранение
подтверждается после перезапуска процесса браузера. Это техническая готовность
к выбранному тесту, а не оценка посетителя сторонними системами.

Посещение засчитывается при доступном содержимом и выполнении требований плана.
Стандартный план требует подтверждённой прокрутки, перехода или короткой страницы,
не требующей прокрутки. План навигации требует внутреннего перехода; повторное
посещение во второй сессии — домена из собственной истории. Частичное посещение
не увеличивает прогресс и не объявляет исправный сайт сетевой ошибкой.

Новые паспорта используют зафиксированный синтетический `utils/profile-base.json`.
Seed, конфигурация, версия каталога и исходный образец воспроизводят идентичность
целиком. Метаданные `generation.baseSample` фиксируют версию, SHA-256 и версию
генератора образца. Время создания не входит в хеш идентичности. Старые паспорта
не регенерируются. Проверка Chromium покрывает все модели каталога, а её ключ
включает версию браузера, каталог, код адаптера и lockfile зависимостей.

`sessionCheck.storageCoverage` описывает проверенные cookies/localStorage/IndexedDB,
политику HTTP-кэша и несохраняемый sessionStorage. В режиме snapshot HTTP-кэш отключён маршрутизацией; в persistent он сохраняется и разрешён версионированным адаптером Playwright. Этот отчёт не измеряет попадания в кэш конкретного сайта и не подтверждает TLS resumption. Service Workers
разрешены: их регистрации и CacheStorage не входят в JSON-снимки; восстановление
в persistent-профиле не аттестуется. Прежние отчёты с `blocked` сохраняются.
Записи старых версий не получают этот отчёт задним числом. Эксперимент с кэшем
в `tests/profile-quality-v2.test.mjs` использует только локальный HTTP-сервер.

Вкладка «Статистика» на странице профилей читает журнал за 1–30 дней, максимум
20 000 последних событий, и явно сообщает об усечении. Успех этапов считается по
завершённым запускам, остановки и неизвестные результаты показаны отдельно.
Длительности относятся к запускам, время подготовки — от создания до готовности.
Метки релиза, модели, режима хранения и плана пишутся для новых запусков; старые
показываются как «Нет данных». Неподтверждённый переход означает также отсутствие
подходящей ссылки, а достижение границы прокрутки не считается неудачным действием.

Проверки: `node --test tests/profile-quality-v2.test.mjs` и, после сборки,
`node tests/profile-quality-v2-ui.mjs`. `ORBIT_TEST_CHROMIUM_EXECUTABLE_PATH`
позволяет явно выбрать установленный браузер. Все тесты используют временные БД.

### Устойчивость прогрева: 14.10.2026

Плановое время чтения не является общим пределом для всех сетевых попыток.
Бюджет сессии: время плана + навигационный таймаут на каждый обязательный
сайт и на максимум три замены; общий предел — 20 минут. Для стандартного
плана 3 минуты / 3 сайта при таймауте навигации 30 секунд это 6 минут.
Отдельные пределы операций, сайта и всего запуска продолжают действовать.

Внутренний переход использует единый бюджет для активации, подтверждения
изменения и ожидания DOM; в прогреве он ограничен 10 секундами. Файлы для
скачивания не выбираются вместо HTML-перехода. При возможности выбирается
видимая ссылка. Занятая резервация сайта не расходует лимит 12 реальных
посещений. Пустая страница отклоняется до долгого чтения; частичное качество
записывается в здоровье донора и получает его обычную паузу.

Если новый запрос главного фрейма подтверждает смену документа во время
scroll/content_check/navigation_guard, потеря DOM/CDP-объекта обрабатывается
как site_navigation с выбором другого донора. Ошибки без такого свидетельства
не маскируются. Успех по-прежнему требует содержимого и действий плана.

Успешное определение IP через страницу в том же proxy-контексте подтверждает
связь для прогрева. Отдельный WORKER_PROXY_CHECK_URL тогда не запрашивается:
недоступность диагностического сайта не должна блокировать доступные доноры.
При выключенной/неудачной проверке IP отдельная проверка сохраняется; режим
required по-прежнему останавливает запуск при ошибке определения IP.

Регрессии: tests/warmup-resilience.test.mjs и tests/warmup-connectivity.test.mjs.

## Сетевой транспорт профиля

`ORBIT_NETWORK_PROBE_URL` задаёт HTTPS API коллектора формата TrackMe (`/api/all`).
Пустое значение отключает внешнее измерение. Адрес не должен содержать credentials,
query или fragment. Коллектор должен непосредственно завершать TLS клиента;
внешний TLS reverse proxy измерит собственный upstream, а не ClientHello браузера.
Адрес задаёт администратор; API диагностики прокси не принимает произвольные URL.
Публичный вариант первого этапа: `https://tls.peet.ws/api/all`.

Измерение делает Chromium в том же BrowserContext, который исполняет профиль,
через настроенный proxy. Node fetch для этого не используется. Два перехода —
initial/follow-up в существующем контексте; повтор не доказывает новое TLS
рукопожатие или session resumption. Проверяются User-Agent и протокол ответа
по CDP. Redirect/невалидный ответ/тайм-аут становятся диагностическим unavailable.
Cookies, значения заголовков, client_random, session_id и сырые ошибки не сохраняются.

JA4 предоставляется коллектором. HTTP/2 хеш `orbit-h2-v1` — SHA-256 от JSON
`{settings,windowUpdates,pseudoHeaderOrder}`; настройки сохраняют порядок,
неизвестные/GREASE SETTINGS исключаются. Это ограниченный отпечаток HTTP/2,
не JA4H и не доказательство идентичности всей реализации HTTP/2.

`ORBIT_NETWORK_HTTP3_URL` задаёт независимый HTTPS стенд с HTTP/3, например
`https://cloudflare-quic.com/cdn-cgi/trace`. Измеряются два перехода, фактический
CDP protocol и объявление Alt-Svc. TCP fallback допустим и не блокирует профиль.
HTTP/SOCKS5 схемы Chromium не обеспечивают UDP Associate; VPN/UDP маршрут этим
измерением не создаётся. Прямой fallback при прокси не добавляется.

`ORBIT_NETWORK_REFERENCE_FILE` — приватный файл формата
`utils/network-reference.example.json`. Записи содержат version=1,
platform=Android, source=physical-device, browserVersion (полная версия), locale,
collectorHost (включая порт), requestKind=document-navigation, measuredAt (ISO),
ja4 и http2Fingerprint (64 hex, алгоритм orbit-h2-v1). Без реальных записей
reference_missing; другой runtime/locale/collector — reference_inapplicable.
Сравнение диагностическое: matched не доказывает физическое устройство.
Синтетическая квалификация Chromium явно помечает транспорт not_measured и
не инициирует внешние запросы. В рабочих проверках результат сохраняется
в fingerprintCheck.network.transport и истории измерений.

Перед обращением к коллектору действует общая SQLite-резервация: не чаще одного
измерения в минуту на hostname/port во всех процессах (два запроса в измерении).
При ограничении новый профиль получает not_measured/probe_throttled, чужой
результат ему не присваивается. Недоступность стенда не исчерпывает попытки задачи.
Ручная кнопка в TCP-диалоге прокси создаёт временный runtime-контрольный профиль,
защищает канал арендами и не сохраняет паспорт/сессию, не меняет IP или TCP-пресет.
CLI: `node --env-file=.env scripts/verify-network-runtime.mjs /private/report.json --proxy PROXY_ID`.
Без --proxy CLI явно проверяет direct-маршрут, а не мобильный прокси.

### Изолированные шрифты и возраст cookies

`node scripts/prepare-browser-fonts.mjs /var/lib/orbit/android-fonts-v1` копирует
установленные Roboto/Noto в отдельный каталог с manifest SHA-256 и fonts.conf.
`FONTCONFIG_FILE=/var/lib/orbit/android-fonts-v1/fonts.conf` применяется к процессам
Chromium, включая квалификацию и перезапуск. Системные шрифты не удаляются.
Ключ квалификации включает fonts.conf и manifest; смена окружения требует новой
квалификации. Набор взят из установленных пакетов, совпадение метрик с физическим
Android без отдельного эталона не подтверждено. Измеряются Canvas, OffscreenCanvas
и DOM-метрики; проверяются также DejaVu Sans, Liberation Sans и Ubuntu.

`ORBIT_COOKIE_MIN_AGE_HOURS=72` или `96` включает дополнительный допуск готовности
по первому наблюдению действующих `_ym_d` и `yandexuid` (0 — выключен).
Cookie идентифицируется по имени, домену, path, partitionKey и SHA-256 значения.
Сырые значения в наблюдениях не сохраняются. Замена/удаление/истечение срока
cookie сбрасывает соответствующее доказательство; дата внутри _ym_d не используется
как основание для допуска. Старым профилям возраст не приписывается задним числом.
История наблюдений сохраняется в снимке и отчёте проверки после перезапуска.
Финальный этап с молодыми cookies сохраняется и ждёт readyAt без удержания
прокси/потока и расходования попыток. При отсутствии нужных cookies повтор через
24 часа; причина видна в разделе профиля. Отсутствие cookies не исправляется их
синтетической установкой. Это политика Orbit, не документированный порог Яндекса.

Существующий сценарий предварительных посещений настроен на 65% запусков,
1–2 уникальных результата из первых пяти, исключая целевой домен. Визит включает
взаимодействия и бюджет ожидания 10–20 секунд от открытия; медленная навигация
может увеличить фактическую длительность. Возврат — нативная история браузера
или закрытие popup. Свайп, гарантированно вызывающий browser Back на Android,
в Linux Chromium не заявляется. ownedOnly исключает внешние посещения.
Сценарий не подтверждает влияние Last Click на ранжирование.

### Переход snapshot → persistent — 2026-10-15

Повторный PATCH с прежним storageMode не выставляет storageResetRequested
и не сбрасывает подтверждение готовности. Реальный переход требует свободной
аренды профиля и новой проверки сохранённой сессии; warmedAt не изменяется.
Импорт snapshot уже существовал в createMobileContext; теперь переход явно
обрабатывается как отдельная проверяемая миграция.

Если текущий сохранённый snapshot помечен storageMode=snapshot, первый запуск
persistent создаёт новый run-каталог, даже если остался старый native current.
Источник — savedSnapshot из проверенного profiles/{id}.json: сохранена исходная
структура JSON для проверки contentHash, до нормализации Zod. Проверяются
profileId, checksum, savedAt и соответствие snapshot.id идентификатору БД.
Переносятся неистекшие и session cookies, localStorage и IndexedDB; затем
verifyRestoredSession проверяет каждое сохранённое значение. В рабочем каталоге
записывается .orbit-seeded-from-snapshot.json с sourceSnapshotId/sourceSavedAt.
Повторный вызов seed в одной попытке не переимпортирует состояние.

Публикация неподтверждённого seed запрещена. Исходный JSON и прежний native
current остаются нетронутыми при ошибке или отмене; следующая попытка может
повторить миграцию. После успешной сессии проверяется отдельный перезапуск,
новые JSON/native-файлы публикуются через существующий durable journal,
а snapshotId и storageResetRequested=false фиксируются в той же SQL-транзакции.
При сбое решение commit/rollback определяется snapshotId БД. Следующий запуск
использует native current без повторного setStorageState. Для предотвращения
потери session cookies при закрытии последнего окна сохраняется пустая вкладка
на время работы persistent-контекста и проверки перезапуска.

JSON не содержит HTTP-кэш, HSTS/TLS tickets, Service Worker и CacheStorage: они
не восстанавливаются из snapshot и не считаются мигрированными. Нативный кэш
начинает накапливаться после перехода; совпадение с прежней браузерной сессией
по этим данным не заявляется. Сохраняются история прогрева, идентичность и
доказательства возраста неизменённых cookies, но готовность требует перепроверки.

### Движение, связанное с touch — 2026-10-15

Motion model v2 остаётся динамикой сессии, не входит в паспорт/identityHash.
Базовые волны спокойного удержания уже имели разные амплитуды/фазы/частоты
между сессиями; 0,25° было суммарной верхней границей, не общей амплитудой.
К ним добавлена отдельная реакция на успешные CDP touchStart/Move/End/Cancel,
включая координатные taps, iframe taps и свайпы. Trial/desktop/отклонённый CDP
ввод не создают touch-реакцию. Наблюдатели разделены по Page, модели — по Context;
остановка, отказ backend и закрытие страницы отписывают наблюдателя.

На touchStart задаются цели beta/gamma ±0,8–2,2°. Изменение скорости пальца
модулирует цель в пределах исходного модуля. TouchMove объединяются с шагом
не менее 90 мс: каждый шаг не добавляет новый полный импульс. Три каскадных
низкочастотных звена дают R(u)=1-(1+u+u²/2)exp(-u), u=t/tau, tau=90–160 мс.
Поза, скорость и ускорение непрерывны; после End/Cancel цель равна нулю,
реакция плавно затухает. Положительное ядро фильтра ограничивает реакцию
значениями целей даже при длинном свайпе/частых жестах. История ограничена
окном 8 секунд, старые изменения сворачиваются в установившееся смещение.

Линейное ускорение вычисляется второй производной того же поступательного
смещения в мировой системе координат, затем переводится в систему устройства.
Настройки стартового пика по device Y/Z — 0,14–0,26 м/с²; смещение выведено
через tau² и пик второй производной R, не подмешано как независимые случайные
числа. Гироскоп вычисляется из производной quaternion, gravity — из ориентации,
accelerometer = gravity + linearAcceleration. С учётом наложения фоновой модели
и последующих изменений цели это не общий жёсткий предел итогового ускорения.

Для каждой сессии выбирается базовый интервал 50–54 мс, каждый следующий таймер
получает джиттер ±2 мс; общие заданные границы 48–56 мс. После завершения
CDP-пакета планируется следующий шаг, просроченные обновления не догоняются
залпом. Время показаний берётся из monotonic performance.now, поэтому задержки
I/O не останавливают физическое время модели. Фактическая задержка включает
работу CDP/планировщика. Верхняя частота Generic Sensor backend остаётся 20 Гц
как настройка симуляции, не характеристика производителя смартфона.

Эти интервалы относятся к обновлению показаний через CDP. Частотой и округлением
DeviceMotion/DeviceOrientation/Generic Sensor DOM-событий управляет Chromium.
Новые JS-события не генерируются, браузерные конструкторы/прототипы не подменяются.
В диагностике разделены updateIntervalMs и nativeEventCadence=browser-controlled;
UI больше не обещает общую амплитуду 0,25° и фиксированную частоту событий 20 Гц.

Параметры — сценарий QA, не дамп датчиков Android. Фоновая модель всё ещё
содержит гармонические составляющие. Совпадение спектра/распределений с живыми
устройствами и результаты антифрод-проверок не подтверждены. Математическая
проверка проверяет единицы и производные; Chromium-тест — trusted события,
изменения показаний от настоящего свайпа и затухание после отпускания.
Спецификация API: https://www.w3.org/TR/orientation-event/ .

## Проверка профилей и поведения: 15 октября 2026

Адаптер Playwright проверяет определения и места вызова функций в установленном
`coreBundle.js`, а не точную строку версии. Неполный или отсутствующий адаптер
даёт `worker_passport_adapter_unavailable` при использовании, без ошибки импорта.
Патч pnpm по-прежнему относится к конкретному upstream-файлу: для новой версии
его нужно перенести и прогнать сетевые/Worker-тесты, а не только поменять номер.
Хеш квалификации считается лениво по установленному coreBundle, версиям
зависимостей и исходникам воркера; patch/lockfile не читаются при импорте.

UA, Client Hints и язык задаются нативно через CDP. Оставшиеся Worker navigator
и WebGL-обёртки сохраняют дескрипторы, native receiver validation, потерю контекста
и исходные сигнатуры через realm-local WeakMap. Это объявленная эмуляция:
совпадение `toString` не означает совпадения физических возможностей, стеков
ошибок или поведения при исследовании из другого realm.

Основные задания и прогрев используют общий PRNG с новым seed из crypto на
каждую сессию. `runTask({behaviorSeed})` и параметры `random` предназначены для
воспроизводимых локальных тестов; production-seed не фиксируется глобально.
Мобильный набор использует `Input.imeSetComposition` и `Input.insertText` только
для подтверждения активной композиции. CDP не предоставляет `imeCommitText`;
`dispatchKeyEvent(char)` дублирует composing text. В проверенном Chromium 154
`compositionend.isTrusted` равен false — флаг не подделывается. Это не физическая
Android-клавиатура. Desktop остаётся на `pressSequentially`. Проверяются фокус,
итоговое значение, единственная попытка исправления и отмена.

Ссылки поиска, блоки чтения и кнопки закрытия хранятся в page-realm Map/WeakMap
под неперечислимыми Symbol. Повторный скан освобождает старые ссылки, замена
элемента не наследует токен. Инициализация Map не очищает токены пагинации.
Служебные data-worker-internal/data-orbit-behavior-block/overlay-close атрибуты
поведенческими модулями не добавляются. Временный target ссылки восстанавливается
в finally/pagehide. Маркеры отдельных диагностических/captcha-модулей не входят
в этот механизм и не были объявлены удалёнными.

Паузы зависят от числа слов и типа блока; прогрев сохраняет 2–4 движения вниз
и необязательное последнее движение вверх. Релевантность — ограниченная эвристика
по intent, заголовкам и хлебным крошкам, без LLM. Юридические, consent, logout,
checkout, sponsored/nofollow и файловые ссылки исключаются. Успех клика требует
подтверждённого изменения URL или стабильного основного контента.

Сохранённый Settings.warmupSites имеет приоритет над `ORBIT_WARMUP_DONOR_SITES`
(JSON-массив минимум трёх публичных HTTP(S) URL). Без обоих используется прежний
пул. Невалидный ENV даёт `invalid_warmup_donor_sites`; недостаточный пул —
`warmup_sites_unavailable`. Проверка доступности идёт через фактическую навигацию
на выделенном прокси. Существующие DB leases, история, экспоненциальный cooldown
и Retry-After сохраняются. `WORKER_WARMUP_INTENT` задаёт необязательный intent.

`restrictNavigation` допускает GET в пределах eTLD+1 по tldts с private suffixes,
при сохранении схемы и порта. Явные approvedRedirects — точные URL. Ответы
редиректов проверяются в browser process до перехода, включая первый popup;
перехват привязан к native BrowserContext id и не отключает HTTP cache.
Captcha POST остаётся одноразовым и привязанным к точному origin/URL; 307/308
не повторяют его на следующем endpoint. Background AJAX и search
allowedSearchHost/outboundDomain сохраняют свои существующие контракты.
Начальные landing redirects runner по-прежнему принимает до включения guard.

`WORKER_MAX_PROFILE_BYTES` / `config.maxProfileBytes` задаёт размер JSON профиля:
по умолчанию 50 000 000 байт, допустимы целые 1–1 000 000 000. Чтение и атомарная
публикация используют одинаковый предел. Превышение даёт `profile_too_large`
и не заменяет предыдущий снимок. Это не лимит всего native Chromium-каталога.

Верификация: `bash prepared/profile-hardening-20261015/verify.sh <label>`
запускает прежние 129 тестов и `pnpm typecheck`. Полный набор, команды, исходные
неудачные прогоны и итоговые результаты находятся в
`prepared/profile-hardening-20261015/` и в обновлённых review-verification отчётах.
Тесты используют локальные серверы, mock captcha и синтетические proxy credentials.
Структурные логи воркера и прогрева удаляют captcha-токены, proxy credentials,
адрес/порт/схему прокси и path/query/fragment URL; proxyId сохраняется для связи
с записью. Диагностический журнал может читать ранее сохранённые адреса.

Previous native profile copies automatically omit `Default/Cache` and `Default/Code Cache` after publication commits. Current copies retain both caches. Cookies, IndexedDB, localStorage, Service Worker/CacheStorage and network identity state remain in the previous copy. Interrupted committed publication resumes this cleanup through the publication journal; rollback never trims the restored current copy. No scheduled maintenance is needed for this policy.

При `ENOSPC`, `EDQUOT`, `SQLITE_FULL` и `profile_disk_full` прогрев ожидает
восстановления дискового пространства (`stage_N_disk_wait`). Эти ошибки
сервера не расходуют попытки профиля и не сбрасывают сохранённый этап или
возраст сессии. Автоматические повторы идут через 5, 10, затем 20 минут.
Ошибки реальной проверки сессии или отпечатка сохраняют прежний лимит попыток.
